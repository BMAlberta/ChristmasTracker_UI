## What changed
- ListService: the shared `error` is removed. New `listsLoadFailure` and `detailLoadFailure` (with `clearListsLoadFailure()`, `clearDetailLoadFailure()`), set only by their own loads, cleared when their own load starts, by their clear method and at teardown. `loadLists(reportingFailure:)` and `refreshLists()` now return the failure. All eight mutations throw only. A follow-up reload or refetch that fails after a successful mutation is logged by operation name and published nowhere; the local effects (the archived list leaves `lists` and the cache) stay. `loadLists` waits for an in-flight lists load (finding D) with a continuation list resumed at completion and at teardown; a waiter whose in-flight load was cancelled starts its own load once (review finding F1). `loadListDetail` records `detailLoadFailure` for a revalidation failure with cached data, a failure with no cache and the guarded not-found.
- ChildService: `error` removed (add and delete only throw); `clearLoadFailure()` turns a failed phase into idle.
- StatsService: `StatsLoadFailure(year:error:)`, `loadFailure: StatsLoadFailure?`, `failure(forYear:)`, `dropBudget(year:)`; a cancelled load records nothing; a success clears the failure only for its own year.
- StatsScreenModel: shows the failure of the selected year only (finding C), owns and cancels its load tasks on disappear (finding C), drops the budget locally after a successful delete (finding B), Edit Budget and Duplicate load the budget first and show a retryable banner on failure or when the year is still missing (finding A), with `retryBudgetCardAction()` and no late completion for another year (review finding F3, F4).
- BudgetEditorModel: loads the lists with `reportingFailure: false` and uses the return value (findings D and E).
- Views (minimal, Story U3 replaces the presentation): DashboardView reads `listsLoadFailure`, holds its archive failure in local state (the `try?` became a catch) and clears both on disappear; ListDetailView reads `detailLoadFailure`, treats the archive as complete (`dismiss()`; `ListArchiveCompletion` is no longer used in production) and clears the failure on disappear; BudgetCardMenu calls the now-async `presentEdit()` and `presentDuplicate()`; BudgetCardView wires the card banner's Try Again to `retryBudgetCardAction()` (this file was not in the Gate 1 list; the banner lives there); ChildrenView clears the load failure on disappear.
Files changed (production): Budgets/ViewState/BudgetEditorModel.swift, Children/Services/ChildService.swift, Children/Views/ChildrenView.swift, Dashboard/Views/DashboardView.swift, Lists/Services/ListService.swift, Lists/Views/ListDetailView.swift, Statistics/Services/StatsService.swift, Statistics/ViewState/StatsScreenModel.swift, Statistics/Views/BudgetCardMenu.swift, Statistics/Views/BudgetCardView.swift. ## Deviations, real bugs found, and notes
- Declared deviation: a follow-up reload or refetch failure after a successful archive, add-member or remove-member is no longer shown (it was shown through the shared error); the next load shows an honest failure. The dashboard error that used to appear after an archive whose reload failed is gone.
- Behavior changes outside error presentation, listed by the reviewer: the dashboard clears its lists failure on every disappear (also when pushing into a list, so a dashboard banner disappears after opening a list and going back; the `.task` reloads only if lists are empty); mutations no longer clear the load failures at their start (a visible lists-load error survives a later mutation); `onDisappear` of the Statistics screen now cancels in-flight stats and budget loads including a pull to refresh; the inline refresh inside `loadLists` no longer opens a nested `service.lists.refreshLists` span; Edit and Duplicate can now perform a forced budgets fetch.
- Real bugs found and fixed in review: F1, F3, F4 above (all in code written in this story).
- Doubt carried to U3: the detail screen shows `detailLoadFailure` only when no detail is shown, so a revalidation failure with cached data is recorded but not yet displayed; U3 renders it through the policy. A waiter that reports (the dashboard) behind a non-reporting in-flight load (the editor) gets the failure back but nothing is stored, so the Lists screen shows no error until the user retries (pinned as intended in ListServiceLoadListsWaitTests; U3 may revisit).
- Coverage gaps accepted: no test for a quiet (`reportingFailure: false`) waiter's own retry after a cancelled load; the editor cancelled-load test cannot prove the waiter path deterministically (if the cancelled load ends before the open task waits, the editor loads directly and the test still passes).
