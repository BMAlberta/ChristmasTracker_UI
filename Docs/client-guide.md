## 2. Required Headers

| Header | Who Sends It | Effect When Missing |
|--------|-------------|---------------------|
| `Authorization: Bearer <token>` | Client (authenticated routes) | 401 `TOKEN_MISSING` on protected routes |
| `X-Client-Platform` | Client | Server treats caller as non-iOS; no refresh token in body; iOS version enforcement skipped |
| `X-Platform` | Client | iOS version enforcement on `/auth/login` and `/auth/refresh` skipped |
| `X-Build` | iOS client | Integer build number for version enforcement; missing → enforcement skipped |
| `X-App-Version` | iOS client | Semver string for version enforcement; missing → enforcement skipped |

**X-Client-Platform** — set to `"ios"` for iOS clients. The server uses this to decide whether to include `refreshToken` in the response body (in addition to the httpOnly cookie). Any other value means no body token.  
Source: `src/routes/auth.routes.ts:22-24`

**X-Platform** — set to `"ios"` for iOS clients. Used by `enforceIosMinimumVersion` on login and refresh to block outdated builds. Non-ios or missing skips enforcement.  
Source: `src/middleware/versionEnforcement.ts:18-23`

**X-Build / X-App-Version** — both optional. If either is missing, enforcement is skipped. Build is parsed as an integer; version is a semver string.  
Source: `src/middleware/versionEnforcement.ts:25-34`

## 3. Authentication

### 3.1 Registration

`POST /tracker/v2/auth/register` · Rate limited (5 req / 15 min per IP+email · `src/middleware/rateLimiter.ts:55-92`)

Required body fields:

| Field | Type | Notes |
|-------|------|-------|
| `email` | string | Valid email format |
| `password` | string | ≥ 8 chars, must contain uppercase, lowercase, digit, and special character |
| `firstName` | string | |
| `lastName` | string | |
| `registrationCode` | string | Shared server-side secret; compared via SHA-256 constant-time comparison to prevent timing attacks |
| `displayName` | string (optional) | Defaults to `firstName + " " + lastName` |
| `rememberMe` | boolean (optional, default `true`) | Same meaning as on login (A16): `true` or omitted sets the persistent refresh cookie (7 days), `false` sets a session cookie. |

Password rules source: `src/utils/password.ts:48-88`  
Registration code check: `src/services/auth.service.ts:38-55`

Response (201) — success envelope, `data` contains the auth payload:

```json
{
  "success": true,
  "data": {
    "user": {
      "id": "uuid",
      "email": "user@example.com",
      "firstName": "Jane",
      "lastName": "Smith",
      "displayName": "Jane Smith",
      "role": "USER",
      "isActive": true,
      "createdAt": "2026-11-02T00:00:00.000Z",
      "updatedAt": "2026-11-02T00:00:00.000Z",
      "lastLoginAt": null
    },
    "accessToken": "<jwt>",
    "expiresIn": 900,
    "refreshToken": "<token>"
  },
  "meta": { "timestamp": "...", "requestId": "...", "sessionId": "..." }
}
```

`expiresIn` is the access token lifetime in seconds, always equal to the token's `exp` minus `iat`, derived from `JWT_EXPIRY` (default 15 minutes, 900).  
`user.email` is always present and never null in the user object returned by register.  
`refreshToken` in the body is **iOS only** — present only when `X-Client-Platform: ios` is sent. It is always set as an httpOnly cookie regardless of platform.  
Source: `__tests__/integration/auth.test.ts` (register tests)

### 3.2 Login

`POST /tracker/v2/auth/login` · Rate limited · iOS version enforced

Required: `email`, `password`  
Optional: `rememberMe` (boolean, default `true`)

- `rememberMe: true` (or omitted) → persistent refresh cookie (Max-Age = `REFRESH_TOKEN_EXPIRY`, default 7 days)
- `rememberMe: false` → session cookie (no Max-Age; browser discards on close)

The `rememberMe` choice is carried through every token rotation.  
Source: `src/services/auth.service.ts:161`, `src/utils/refreshCookie.ts`

Response (200): same envelope shape as register — `{ success, data: { user, accessToken, expiresIn, refreshToken }, meta }`. `expiresIn` is the access token lifetime in seconds, always equal to the token's `exp` minus `iat`, derived from `JWT_EXPIRY` (default 15 minutes, 900). `user.email` is always present and never null. `refreshToken` body field is iOS only.  
Source: `__tests__/integration/auth-remember-me.test.ts`

**Error responses:**
- `400 VALIDATION_ERROR` — malformed or oversized request body.
- `401 UNAUTHORIZED` — wrong password or unknown email.
- `403 ACCOUNT_DISABLED` — account exists but has been deactivated by an administrator. No session is created: show the user a message (the client is already on the login screen). Discard any stored refresh token for this account, because a refresh would also return 403; re-attempting continues to fail until an administrator re-enables the account. On an authenticated call, a 403 `ACCOUNT_DISABLED` ends the session (see §4).
- `426 UPGRADE_REQUIRED` — iOS only; build/version is below the enforced minimum (see §3.6).
- `429 RATE_LIMIT_EXCEEDED` — too many login attempts; respect `Retry-After`.

### 3.3 Token Refresh

`POST /tracker/v2/auth/refresh` · iOS version enforced

The server prefers the httpOnly cookie; falls back to `refreshToken` in the body. iOS clients that cannot use cookies send the token in the body.  
Source: `src/routes/auth.routes.ts:255-258`

Optional body:
```json
{ "refreshToken": "<token>", "deviceFingerprint": "<fingerprint>" }
```

Response (200):
```json
{
  "success": true,
  "data": {
    "user": { ... },
    "accessToken": "<new-jwt>",
    "expiresIn": 900,
    "refreshToken": "<new-token>"
  },
  "meta": { ... }
}
```

`refreshToken` in the body is only present for `X-Client-Platform: ios`.  
`expiresIn` is the access token lifetime in seconds, always equal to the token's `exp` minus `iat`, derived from `JWT_EXPIRY` (default 15 minutes, 900).  
`user.email` is always present and never null in the user object returned by refresh and GET /auth/me.  
Source: `src/routes/auth.routes.ts:277`

The server always sets the new refresh token as an httpOnly cookie. The old token is marked rotated, not immediately deleted (see grace window below).

**Token lifetimes:**

| Parameter | Default | Source |
|-----------|---------|--------|
| Access token (JWT) | 15 minutes | `JWT_EXPIRY` env — `src/config/env.ts:22`. This is also the source of `expiresIn` in login, register, and refresh responses. |
| Refresh token | 7 days sliding | `REFRESH_TOKEN_EXPIRY` env — `src/config/env.ts:24` |
| Grace window | 45 seconds | `REFRESH_GRACE_SECONDS` env — `src/services/auth.service.ts:200-208` |
| Absolute session cap | 90 days from first login | `REFRESH_ABSOLUTE_MAX_DAYS` env — `src/services/auth.service.ts:221-226` |

**Grace window detail:** After a token is rotated, it remains valid for 45 seconds. This handles concurrent refresh calls or network retries where the same token is presented twice. Within the window, the server issues another new token. Outside the window, it treats the replay as a possible token theft and revokes the entire chain.  
Source: `src/services/auth.service.ts:199-210`, `__tests__/integration/auth.test.ts`

**Absolute session cap:** After 90 days, the entire chain is revoked regardless of activity. The user must log in again.  
Source: `__tests__/integration/auth-session-cap.test.ts`

**Error responses:**
- `400 VALIDATION_ERROR` — malformed or oversized request body.
- `401` — expired, invalid, missing, or revoked refresh token (see §3.6 for specific codes).
- `403 ACCOUNT_DISABLED` — the account associated with the refresh token has been deactivated. The client must redirect to the login screen and discard stored tokens.
- `426 UPGRADE_REQUIRED` — iOS only; build/version is below the enforced minimum (see §3.6).
- `429 RATE_LIMIT_EXCEEDED` — too many requests; respect `Retry-After`.

### 3.4 Token Storage Guidance

**iOS:** Store the refresh token from the response body in the iOS Keychain, protected with biometric authentication (Face ID / Touch ID). Always send `X-Client-Platform: ios` to receive the body token. Make API calls with `URLSession` (not `WKWebView`). iOS must disable cookie handling: set `URLSessionConfiguration.httpShouldSetCookies = false` and supply no cookie storage — if cookies are enabled the server's httpOnly cookie takes precedence over the body token and the client loses the ability to provide the refresh token independently.

**Web:** Do NOT store the refresh token in `localStorage` or `sessionStorage`. Use the httpOnly cookie (automatically managed by the browser). Keep the access token in memory only. Never write either token to persistent storage.

**Web CORS configuration:** CORS is controlled by `CORS_ORIGIN` only — a comma-separated list of allowed origins. Each entry must be scheme, host and optional port with no trailing slash (e.g. `http://localhost:5173` or `https://tracker.bmalberta.com`); entries with a trailing slash, path, query string or fragment are rejected at startup. Origin matching is an exact string comparison. In production every origin must use https and localhost is not permitted. For a matching origin, the server echoes exactly that origin in `Access-Control-Allow-Origin` and never responds with `*`. Credentials (`credentials: "include"`) are always allowed. Allowed request headers are `Content-Type`, `Authorization`, `X-Request-Id`, `X-Session-Id`, `sentry-trace` and `baggage`. Allowed methods are `GET`, `POST`, `PUT`, `PATCH`, `DELETE` and `OPTIONS`. Preflight results are cached for 600 seconds. Readable response headers (exposed to JavaScript via `access-control-expose-headers`) are `X-Request-Id`, `X-Session-Id`, `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` and `Retry-After`.  
Source: `src/app.ts` (CORS block), `src/config/env.ts` (CORS_ORIGIN rules)

**Refresh cookie attributes (web):** The refresh token cookie is HttpOnly, SameSite=Strict, Secure only in production, host-only (no `Domain` attribute), with `Path=/tracker/v2/auth` so that both `/auth/refresh` and `/auth/logout` receive it automatically. When `rememberMe: true` the cookie has a 7-day Max-Age renewed on every rotation; when `rememberMe: false` the cookie is a session cookie with no Max-Age and the browser discards it on close. Register honors `rememberMe` exactly like login, so a web client with "Keep me signed in" off should send `rememberMe: false` on register as well.  
Source: `src/utils/refreshCookie.ts`

**Single-flight refresh:** If multiple requests receive a 401 simultaneously, only one should call `/auth/refresh`. Others should queue and resume once the new access token is available. The 45-second grace window is designed to absorb natural races between concurrent requests sharing the same token.

### 3.5 Logout

`POST /tracker/v2/auth/logout` · Requires `Authorization` header

The handler revokes the refresh-token chain for a refresh token sent in the `refreshToken` cookie or, when there is no cookie, in the JSON body field `refreshToken`, then clears the cookie. A logout that carries no refresh token revokes nothing and still returns 200.

**Web clients** rely on the httpOnly cookie. The cookie's `Path=/tracker/v2/auth` covers both `/auth/refresh` and `/auth/logout`, so the browser sends it to logout automatically. The server revokes the refresh-token chain through the cookie and clears the cookie on a 200. No body is needed.

**iOS clients must NOT send the refresh token to logout** (no cookie, because cookie handling is disabled, and no `refreshToken` in the body). iOS keeps its biometric-protected Keychain refresh token across an explicit logout so Face ID can sign the user in again (decision A15). Sending the token would revoke the session and break Face ID sign-in after logout. The server session therefore lives until the 7-day sliding expiry or the 90-day absolute cap; an administrator can revoke every session of a user with `npm run user:reset-password`.

**iOS logout sequence:**
1. Call `POST /auth/logout` with only `Authorization: Bearer <accessToken>` and no body.
2. Discard the access token from memory and keep the Keychain refresh token.
3. Show the login screen.
4. A 401 from logout (expired access token) can be ignored because nothing needs to be revoked.

Response (200):
```json
{
  "success": true,
  "data": { "message": "Successfully logged out" },
  "meta": { ... }
}
```

Source: `src/routes/auth.routes.ts`, `src/services/auth.service.ts`

### 3.6 Exact 401 and 426 Behaviors

**401 responses and their codes:**

| Code | String | Cause |
|------|--------|-------|
| 1002 | `TOKEN_EXPIRED` | JWT access token has passed its expiry |
| 1003 | `TOKEN_INVALID` | JWT is malformed or has an invalid signature |
| 1004 | `TOKEN_MISSING` | `Authorization` header absent |
| 1005 | `REFRESH_TOKEN_EXPIRED` | Refresh token has passed its expiry or the 90-day cap was reached |
| 1006 | `REFRESH_TOKEN_INVALID` | Refresh token not in the database (revoked or never existed) |
| 1007 | `SESSION_EXPIRED` | Chain revoked due to reuse outside grace window |
| 1013 | `REFRESH_TOKEN_MISSING` | `/auth/refresh` called with no cookie and no body token |

Source: `src/middleware/auth.ts`, `src/services/auth.service.ts`

**What to do on 401 mid-request:**
1. Call `/auth/refresh` to rotate tokens.
2. Replay the original request with the new access token.
3. If refresh returns 401 (codes 1005, 1006, 1007) or 403 (`ACCOUNT_DISABLED`), redirect to the login screen and discard stored tokens.

**426 (Upgrade Required) on login or refresh (iOS only):** The client build/version is below the enforced minimum. The error `details` contain:
- `minimumBuild`, `minimumVersion`
- `latestBuild`, `latestVersion`
- `manifestUrl`, `ipaUrl`

Display an update prompt and use `ipaUrl` or `manifestUrl` to deep-link to the update. Do not retry — the only resolution is updating the app.  
Source: `src/middleware/versionEnforcement.ts`, error code 1014 in `src/utils/errors.ts`

## 4. Error Envelope and Code Mapping

All errors use this shape:

```json
{
  "success": false,
  "error": {
    "code": 1002,
    "errorCode": "TOKEN_EXPIRED",
    "message": "Your session has expired. Please log in again",
    "details": {}
  },
  "meta": {
    "timestamp": "2026-11-02T00:00:00.000Z",
    "requestId": "req-abc123",
    "sessionId": "ses-abc123"
  }
}
```

Source: `src/utils/response.ts:97-123`

Every operation in the OpenAPI spec documents a `500` response using this same `Error` envelope (C12). Clients should handle 500 responses generically — they represent unexpected server errors.

**Middleware statuses on authenticated endpoints (C15).** Every operation secured with `bearerAuth` can return any of the following from shared middleware before the handler runs:

| Status | ErrorCode | Cause |
|--------|-----------|-------|
| 401 | see §3.6 | Missing, expired, or invalid access token |
| 403 | `ACCOUNT_DISABLED` | Account is deactivated; end the session (clear the tokens and show the login screen) |
| 404 | `USER_NOT_FOUND` | Means only that the account behind the token no longer exists (C17); end the session and redirect to login. `PERSON_NOT_FOUND` is a normal not-found (for example `GET /users/{id}`); do not end the session on it |
| 429 | `RATE_LIMIT_EXCEEDED` | General rate limit exceeded; respect `Retry-After` |
| 500 | `INTERNAL_ERROR` | Unexpected server error |
| 400 (body ops) | `INVALID_INPUT` or `VALIDATION_ERROR` | Operations with a request body: 400 INVALID_INPUT or VALIDATION_ERROR, including an oversized or malformed body; the envelope carries requestId and sessionId like every other error |

**Which of these end the session.** On an authenticated call, a `403 ACCOUNT_DISABLED` or a `404 USER_NOT_FOUND` ends the session: clear the tokens and show the login screen (client action `re-login`). On the login endpoint itself, `ACCOUNT_DISABLED` is shown to the user as a message, because there is no session to end. A `404 PERSON_NOT_FOUND` is a normal not-found (client action `treat as not found`) and never ends the session.

Clients must handle all five on every call to a `bearerAuth` endpoint. Public endpoints (register, login, refresh, version-check) can still return 429 and 500 from their own rate limiters and the global error handler.

**426 (Upgrade Required) — `VersionOutdatedError` shape:** The 426 response uses a specialised envelope. `error.details` is a `VersionOutdatedDetails` object:

```json
{
  "success": false,
  "error": {
    "code": 1014,
    "errorCode": "VERSION_OUTDATED",
    "message": "App version is out of date",
    "details": {
      "minimumVersion": "2.0.0",
      "minimumBuild": 10,
      "latestVersion": "2.1.0",
      "latestBuild": 20,
      "manifestUrl": null,
      "ipaUrl": null
    }
  },
  "meta": { ... }
}
```

Source: `src/config/swagger.ts` (`VersionOutdatedError`, `VersionOutdatedDetails` schemas, C12)

**Code mapping:** See [Docs/error-codes.md](error-codes.md) for the full table: numeric code, string code, HTTP status, default message, thrown-in files, status (ACTIVE/UNUSED/OBSOLETE), and recommended client action.

**Forward compatibility:** If the client receives an error code it does not recognise, it MUST NOT crash. Decode unknown codes to a generic "unexpected error" UI state. New codes will always be added within the existing category blocks (1xxx auth, 2xxx authorization, 3xxx validation, etc.). The `errorCode` string is stable; the numeric code is an integer in the range 1000–9999.

**Client action summary:**

| Action | Meaning |
|--------|---------|
| `re-login` | Drop all stored tokens; redirect to login screen |
| `refresh once and replay; if that fails, re-login` | Try one token refresh and replay the original request; redirect to login only if the refresh also fails |
| `force update` | Block the app; show update prompt with `details.minimumVersion` and `details.ipaUrl` |
| `treat as not found` | Resource does not exist or caller lacks permission (server never reveals which); show a generic "not found" state |
| `back off and retry` | Transient error; respect `Retry-After` header if present, otherwise use exponential back-off |
| `show message` | Display `error.message` to the user |
| `not an error: appears in warnings[]` | Not an error response; appears in `warnings[]` of a 200 OK when a purchase would exceed budget (see §7.6) |

## 5. Response Envelope, Pagination, and Data Formats

### 5.1 Success Envelope

```json
{
  "success": true,
  "data": { ... },
  "warnings": [ ... ],
  "meta": {
    "timestamp": "2026-11-02T00:00:00.000Z",
    "requestId": "...",
    "sessionId": "...",
    "filteredCount": 42
  },
  "pagination": { ... }
}
```

`warnings` is only present on budget-overage responses.  
Extra `meta` fields (e.g. `filteredCount`, `nextCursor`) are route-specific.  
Source: `src/utils/response.ts`

### 5.2 Pagination

Purchase history (`GET /tracker/v2/purchases`) uses **cursor-based pagination**:

- Query params: `limit` (integer, 1–100, default 50), `cursor` (opaque base64 string)
- Response `meta` contains: `filteredCount`, `filteredTotal`, `nextCursor` (null when no more pages)
- Pass `nextCursor` as `cursor` in the next request. Do NOT construct or decode cursors manually.

Source: `src/routes/purchase.routes.ts:73-86`, `src/types/responses.ts:270-274`, `__tests__/integration/purchases-history.test.ts` ("response envelope shape" describe block)

List, item, member, and budget routes return all results in a single response without pagination. **UNVERIFIED:** no explicit page size limit is enforced on these routes.

### 5.3 Date Format

All dates in responses are ISO 8601 UTC strings (`"2026-11-02T00:00:00.000Z"`). The `year` field on lists is a plain 4-digit integer.  
Source: `src/types/responses.ts`

### 5.4 Money Format (S11, C11)

| Direction | Format | Notes |
|-----------|--------|-------|
| Client → Server | Floating-point dollar amount | e.g. `349.99` · at most two decimal places · max value `999999.99` |
| Server → Client | JSON `number` | e.g. `349.99` — always a number, never a Decimal string |
| Internal storage | Integer cents | `toCents(349.99)` → `34999` |

**S11 rule (request):** The server rejects amounts with more than two decimal places with `400 INVALID_PRICE` (code 3007). The field name is reported in `error.details.field`. Do not rely on the server to round — use a decimal type on the client side and round to two decimal places before sending. Values like `0.30000000000000004` (IEEE 754 drift from `0.1 + 0.2`) or `1e-7` (exponent notation) are rejected even if mathematically valid.  
Source: `src/types/schemas.ts` (`moneyAmountSchema`), `src/middleware/validate.ts`, `__tests__/integration/money-validation.test.ts`

**C11 rule (response):** Money fields in responses (`expectedUnitPrice`, `totalCost`, `totalBudget`, `maxSpend`, `PurchaseHistoryRow.totalCost`) are serialized as JSON numbers with at most two decimal places. They are never returned as strings even though Prisma stores them as `Decimal` internally. Parse them as numbers directly; do not expect string formatting.  
Source: `src/utils/money.ts` (`toMoneyJson`), `__tests__/integration/contract-c11-c14.test.ts`

## 6. Capability Flags and Privacy Rules

### 6.1 Capability Flags on ListSummary

Every `ListSummary` response includes per-viewer boolean flags:

| Flag | True When |
|------|-----------|
| `canSeeGiftActivity` | Non-blind owner/co-owner or ACTIVE MEMBER-role member |
| `canPurchase` | Non-blind owner/co-owner or ACTIVE MEMBER-role member |
| `canAddOffList` | ACTIVE MEMBER-role member only |
| `canSeeOffList` | Non-blind owner/co-owner or ACTIVE MEMBER-role member |
| `canCreateItem` | Owner, co-owner (blind or not), or ACTIVE MEMBER-role member |
| `canSeeMembers` | Owner, co-owner (blind or not), or ACTIVE MEMBER-role member; false for VIEWER-role members and PUBLIC non-members (P22) |
| `canEditList` | Owner or co-owner (blind or not): `PATCH /lists/{id}` (P23, L14) |
| `canDeleteList` | Owner or co-owner (blind or not): `DELETE /lists/{id}`, which archives the list (P23, L14) |
| `canManageMembers` | Owner or co-owner (blind or not): add members and remove other members (P23, L8) |
| `canSetCoOwner` | Owner only: send `coOwnerEmail` on `PATCH /lists/{id}` (P23, L12) |
| `canLeaveList` | ACTIVE MEMBER-role or VIEWER-role member; false for the owner, co-owner and every non-member (P23, L9) |
| `myRole` | `"owner"` · `"co-owner"` · `"member"` · `"viewer"` |
| `isRecipient` | True when the viewer is the list's recipient |

**Drive UI elements from flags, not from `myRole`.** Roles may gain or lose rights in future versions.  
The same capability flags appear on both `ListSummary` and `ListDetail`.

**C14 — memberCount vs members:** `ListSummary` (returned by `GET /lists`) carries `memberCount: number` — the count of ACTIVE memberships — not a `members` array. `ListDetail` (returned by `GET /lists/{id}` and `POST /lists`) carries the full `members` array AND `memberCount`. Clients that previously accessed `ListSummary.members` must switch to `GET /lists/{id}` to retrieve the full member list.  
**P22 — members only when `canSeeMembers` is true:** `ListDetail.members` is present only when `canSeeMembers` is `true` and is absent otherwise (the key is not sent, and it is never an empty array). Use `memberCount` when `canSeeMembers` is `false`, and call `GET /lists/{id}/members` only when it is `true` (the endpoint returns 403 otherwise).  

**List management rights (P23):**

| Action | Endpoint | Flag | Who | On an ARCHIVED list |
|--------|----------|------|-----|---------------------|
| Edit name, theme, visibility or status | `PATCH /lists/{id}` | `canEditList` | Owner, co-owner | `false`; the server refuses with 422 `CANNOT_EDIT_ARCHIVED_LIST` |
| Delete (archives the list) | `DELETE /lists/{id}` | `canDeleteList` | Owner, co-owner | `false`; the server still accepts the call |
| Add a member | `POST /lists/{id}/members` | `canManageMembers` | Owner, co-owner | `false`; the server still accepts the call |
| Remove another member | `DELETE /lists/{id}/members/{userId}` | `canManageMembers` | Owner, co-owner | `false`; the server still accepts the call |
| Set or clear the co-owner | `PATCH /lists/{id}` with `coOwnerEmail` | `canSetCoOwner` | Owner only | `false`; the server refuses with 422 `CANNOT_EDIT_ARCHIVED_LIST` |
| Leave the list | `DELETE /lists/{id}/members/{your userId}` | `canLeaveList` | ACTIVE MEMBER-role or VIEWER-role member | unchanged; allowed on a list of any status |

Archived lists are read-only in the app. The server refuses edits to an archived list with 422, but still accepts delete and member changes, so the flags are deliberately stricter than the server there. Deleting archives, so a deleted list is an ARCHIVED list. The server enforces every action regardless of the flags.  
`POST /lists/{id}/members` returns only the new `MemberSummary`, and `DELETE /lists/{id}/members/{userId}` and `DELETE /lists/{id}` return only a message, so refetch `GET /lists/{id}` or adjust `memberCount` yourself after these calls.  
Source: `src/utils/privacy.ts`, `src/types/responses.ts:71-104`, `src/services/list.service.ts`, `__tests__/integration/contract-c11-c14.test.ts`

### 6.2 Blind Viewers

A viewer is **blind** (cannot see gift activity) when:
- The viewer is the list's recipient, OR
- The viewer is the owner/co-owner of a list whose recipient has credentials (non-null email and passwordHash)

Blind viewers have `canSeeGiftActivity: false`, `canPurchase: false`, `canAddOffList: false`, and `canSeeOffList: false`. They can see the list and its items, but:
- `itemCount` and `purchasedCount` are absent from `ListSummary` and `ListDetail`
- All items are returned with `status: "AVAILABLE"` regardless of real status
- `updatedAt` is omitted from each item response
- No off-list items appear in item lists
- No purchase details in any response

Source: `src/utils/privacy.ts:1-11, 61-82`, `src/services/list.service.ts:693-696`, `src/services/item.service.ts:463-465`, `__tests__/unit/privacy.unit.test.ts`

### 6.3 VIEWER-role Members and PUBLIC Non-members

Members with `role: "viewer"` and authenticated non-members of PUBLIC lists face the same restrictions:

- `canSeeGiftActivity: false`, `canPurchase: false`, `canAddOffList: false`, `canSeeOffList: false`
- `itemCount` and `purchasedCount` are absent from `ListSummary` and `ListDetail`
- Items appear with `status: "AVAILABLE"` (real status hidden); `updatedAt` is omitted
- No off-list items in item lists
- `GET /lists/{id}/members` returns 403 for VIEWER-role members (L9)
- PUBLIC non-members can read but not write — any POST/PATCH/DELETE on a PUBLIC list returns 403 (P18)

Source: `src/utils/privacy.ts`, `src/services/item.service.ts:460-468`, `Docs/privacy-matrix.md`

### 6.4 What All Non-gift-activity Viewers Never Receive

This applies to blind owners/co-owners, VIEWER-role members, and PUBLIC non-members equally:

- No `itemCount` on `ListSummary` or `ListDetail`
- No `purchasedCount` on `ListSummary` or `ListDetail`
- Items show `status: "AVAILABLE"` only — real status is never disclosed
- `updatedAt` is absent from each item response
- No off-list items in item lists
- No purchases array in individual item responses

The server enforces all of this server-side; clients must not attempt to infer privacy state from the `myRole` field.  
Source: `src/services/list.service.ts:693-696`, `src/services/item.service.ts:460-476`

### 6.5 When the Server Returns 404 vs 403

The server distinguishes between "you cannot do that on something you can see" (403) and "that resource is hidden or absent" (404).

**404 — resource is hidden or absent:**
- Non-members trying to access a non-PUBLIC list (PRIVATE, INVITE_ONLY, FRIENDS_ONLY) — existence is never confirmed (P14, P16)
- A caller accessing someone else's purchases or budgets, or a stranger's user profile (see §7.10 for the tiers) — the resource appears non-existent to protect privacy

**403 — caller is an authenticated list participant lacking a specific capability:**
- A MEMBER-role or VIEWER-role member trying to edit or delete the list
- A VIEWER-role member trying to list members (`GET /lists/{id}/members`)
- A VIEWER-role member trying to post items or purchases
- Any self-list owner/co-owner trying to purchase from their own list (`CANNOT_PURCHASE_OWN_LIST`)
- Any authenticated non-member of a PUBLIC list trying to write (POST/PATCH/DELETE) — P18

**Client guidance:** Treat 404 as "not found or not yours"; show a generic "not found" state. Treat 403 as "you cannot do that here"; show an appropriate permission message.  
Source: `Docs/privacy-matrix.md`, `__tests__/integration/privacy.test.ts`

### 7.6 Purchase with Budget Confirmation Flow

**Step 1 — Initial attempt:**

```
POST /tracker/v2/items/<itemId>/purchases
Authorization: Bearer <token>
Content-Type: application/json

{ "quantity": 1, "totalCost": 349.99, "storeName": "Best Buy" }
```

**If within budget** — Response (201):
```json
{
  "success": true,
  "data": { "status": "created", "purchase": { ... }, "requiresConfirmation": false }
}
```

**If over budget** — Response (200):
```json
{
  "success": true,
  "data": { "status": "confirmation_required", "purchase": null, "requiresConfirmation": true },
  "warnings": [{
    "code": 6002,
    "warningCode": "BUDGET_OVERAGE_WARNING",
    "level": "recipient",
    "severity": "warning",
    "requiresConfirmation": true,
    "confirmationToken": "<opaque-token>",
    "details": {
      "recipientId": "...",
      "recipientName": "Tommy",
      "budgetLimit": 500,
      "currentSpent": 450,
      "purchaseAmount": 349.99,
      "overage": 299.99
    }
  }]
}
```

No purchase is created on the 200 response. The caller must explicitly confirm.

`level` is either `"recipient"` (per-recipient budget exceeded) or `"total"` (overall budget exceeded). Multiple warnings may be present simultaneously.

**Step 2 — Resubmit with confirmation token:**

```
POST /tracker/v2/items/<itemId>/purchases
Authorization: Bearer <token>
Content-Type: application/json

{
  "quantity": 1,
  "totalCost": 349.99,
  "storeName": "Best Buy",
  "confirmationToken": "<token-from-any-warning>"
}
```

The token binds user, item, recipient, quantity, and amount in cents and expires after **5 minutes**. Use any one warning's `confirmationToken` if multiple warnings are present.  
Source: `__tests__/integration/purchase-budget.test.ts`, `src/utils/budgetConfirmationToken.ts:18`

## 8. Version Check Usage

```
GET /tracker/v2/app/version-check?platform=ios&version=1.2.3&build=42
```

No authentication required. Rate limited to 60 req/min. Supports ETag/If-None-Match for 304 responses.  
Source: `src/routes/app-version.routes.ts:10-15, 83-87`

**Recommended call schedule:**
- Cold start
- App resume from background
- Every 6 hours in the background — **UNVERIFIED:** no server-enforced schedule; client-side recommendation
- On receiving a 426 response

**Response:**
```json
{
  "success": true,
  "data": {
    "state": "ok",
    "platform": "ios",
    "minimumVersion": "1.0.0",
    "recommendedVersion": "1.2.0",
    "latestVersion": "1.2.3",
    "minimumBuild": 10,
    "latestBuild": 42,
    "manifestUrl": null,
    "ipaUrl": null,
    "releaseNotes": null,
    "enabled": true,
    "updatedAt": "2026-11-01T00:00:00.000Z"
  }
}
```

**States:**

| State | Meaning | Client Action |
|-------|---------|---------------|
| `ok` | Client is current or above minimum | Proceed normally |
| `update_recommended` | Newer version available | Prompt but do not block |
| `force_update` | Client is below minimum | Block and prompt for update |

A disabled or unknown platform always returns `state: "ok"` with zero-value fields.  
Source: `src/services/version.service.ts:46-48`

**ETag caching:** Server sets `Cache-Control: public, max-age=60`. Send `If-None-Match` with the cached ETag to receive a 304 when nothing has changed.  
Source: `src/routes/app-version.routes.ts:83-87`

**426 on login or refresh (iOS only):** `error.details` contains `minimumBuild`, `minimumVersion`, `latestBuild`, `latestVersion`, `manifestUrl`, `ipaUrl`. Use `ipaUrl` or `manifestUrl` to deep-link the user to the update. Do not retry the request.  
Source: `__tests__/integration/version-enforcement.test.ts`, `__tests__/integration/version-check.test.ts`

## 9. Rate Limits and Retry Guidance

| Limiter | Window | Max | Scope |
|---------|--------|-----|-------|
| Auth | 15 min | 5 req | `/auth/register`, `/auth/login` — keyed per IP + email |
| General | 15 min | 100 req | All other routes — keyed per session ID or IP |
| Version check | 1 min | 60 req | `/app/version-check` |

Source: `src/middleware/rateLimiter.ts:11-48, 55-92`, `src/routes/app-version.routes.ts:10-15`

**On 429:**
1. Read `error.details.retryAfter` (seconds). Respect the `Retry-After` HTTP header if present.
2. If neither is available, use exponential back-off starting at 1 second.

**`RateLimit-*` headers:** The server sets standard `RateLimit-Limit`, `RateLimit-Remaining`, and `RateLimit-Reset` headers (`standardHeaders: true`). Read `RateLimit-Remaining` to back off before hitting the limit.  
Source: `src/middleware/rateLimiter.ts:15-16`

## 10. Known Gaps and Deferrals

These features are not implemented. Do not build client UI for them. Surface appropriate messaging instead.

| Feature | Status | Client Guidance |
|---------|--------|-----------------|
| **Invitation emails** | Not implemented | Membership is granted immediately; `MemberSummary.status` is `"ACTIVE"` on the same response as the add-member call. Show no "invitation pending" state. |
| **Search** | Not implemented | No `/search` endpoint exists. Do not display a search field. |
| **Push notifications** | Not implemented | `PUSH_NOTIFICATION_ERROR` (7002) is defined but no push-token registration endpoint exists. |
| **Email notifications** | Not implemented | `EMAIL_SERVICE_ERROR` (7001) is defined but no email-trigger endpoints exist. |
| **Backend biometric auth** | Not implemented | `INVALID_BIOMETRIC_TOKEN` (1015) is defined but no biometric endpoint exists. |
| **Self-service password reset** | Not implemented | "Forgot password?" is not self-service. Clients should display: _"Forgot your password? Contact your administrator to have it reset."_ Administrators use `npm run user:reset-password -- --email <address>` to generate a temporary password. |
