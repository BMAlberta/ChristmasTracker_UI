# I4c: Clearing a tracking number, and a delete that refreshes even if the user leaves
Track: iOS. Depends on: I4b (merged) and the contract sync on this branch (decisions revision 34: S15). Blocks: nothing.
Contract state: CONFORMANT. API models come only from the generated client.

Why: (1) After I4b the app treats an empty tracking field as "unchanged", so a saved tracking number can never be removed. Decision S15 (merged at backend fe1a85f, spec checksum 494100e86e46) fixes the contract: on PATCH /purchases/{id} (updatePurchase) and on PATCH /purchases/{id}/shipping (updatePurchaseShipping) an empty string CLEARS the field; it is stored and returned as null (never ""); an omitted field is unchanged; null is still a 400. Notes can be cleared on updatePurchase only (the shipping body has no notes); trackingNumber can be cleared on BOTH operations. The generated client can send "" but never null, which is exactly the rule. No shape and no operationId changed, so regeneration changes only comments and descriptions. (2) I4b found a real defect: if the user swipes back while a delete is in flight and the delete succeeds, the refresh of the item, the items and the list does not run (it ran from the view's task, which is cancelled when the view goes away), so the item card keeps the deleted row until the next refresh.

Server facts (client guide 7.7, decisions S14 and S15, P11; confirm each against the synced files): a purchase's trackingNumber and notes come back as a string or null; after S15 a cleared field is null, but rows written before S15 may still carry "" (treat "" and null both as empty and show nothing). DELETE /purchases/{id} returns the deleted purchase including its item reference {id, name, listId} but not the item's updated status or counts, so the client refetches the item. updatePurchase accepts only notes (up to 1000 characters) and trackingNumber (up to 100); updatePurchaseShipping requires shippingStatus and accepts trackingNumber (up to 100).

Scope
1. Story P0: regenerate from the synced contract (comment and description changes only).
2. Story A: pure rules for clearing a tracking number (the change type, the dirty check, the request builder, the display of empty values).
3. Story B: the repository and mock behavior for "" and null, tested through the real factory-built client.
4. Story C: the Shipping section clears the tracking number, and the delete's follow-up refresh runs even when the user leaves the screen.
5. Story D: tidy the stale comments listed in the I4b legacy-deletion report, then the handoff and the real-mode check.

Decisions
- UI RULES FOR NEW CODE (banked polish backlog; they apply to everything new or rewritten in this package; older screens are not refactored): (1) every confirmationDialog is attached to the control that triggers it; (2) errors are scoped: a mutation error is thrown to the initiating view and held in its local state (an InlineErrorBanner inside that screen or section) and disappears on dismiss, retry success, or leaving the screen; nothing is published in a shared service error that another screen reads; (3) destructive actions use role: .destructive with Color.destructiveColor; (4) errors use the existing InlineErrorBanner.
- Tracking number change: replace the "empty means unchanged" rule with an explicit change type for the tracking number (unchanged, set(String), clear) derived by a pure function from the original value and the edited text, exactly like PurchaseNotesChange: the original is empty (nil or "") and the edited text is empty or whitespace: unchanged; the original is non-empty and the edited text is empty or whitespace: clear; otherwise set(trimmed) when it differs from the original trimmed value, else unchanged. The field limit stays 100 characters. Whitespace-only counts as empty. The shipping Save is enabled when the status changed OR the tracking change is not unchanged.
- Request rules (updatePurchaseShipping): the body always carries shippingStatus (required) and carries trackingNumber ONLY when the change is set(value) (the value) or clear (the empty string ""); an unchanged tracking number is omitted. A tracking-only edit still sends the current status. updatePurchase (the Notes section) keeps its I4b behavior (notes only; "" clears notes; never trackingNumber); the UI never sends trackingNumber to updatePurchase.
- Display: nil and "" tracking numbers and notes both show as empty (no placeholder text beyond the field's own prompt); after a save the screen updates from the RETURNED purchase, so a cleared tracking number shows as an empty field and a disabled Save.
- Mock: MockPurchaseManager mirrors S15: on both operations an empty string clears trackingNumber (stored as nil, returned as nil), notes clear only on updatePurchase, an omitted field is unchanged, and the mock never stores "".
- The delete flow's follow-up refresh must not depend on the view staying on screen: the refresh plan (item detail, items, list detail) runs from the service or the model in a task that is NOT cancelled by the view disappearing, but IS still protected by the existing session guards (generation, cancellation at teardown, nothing written after the session ended or a user switch). If the user leaves the screen while the delete is in flight, the delete still completes and the refresh still runs; a 404 on the item refetch still drops the item from the caches; a failed refresh never turns the delete into an error. Do not disable the swipe-back gesture as the fix.
- No logging of tracking numbers, notes, ids or raw errors; session safety and hermetic tests as before.

Non-goals: the idempotency key (parked by the API team), clearing any other field, editing quantity, cost, store name or confirmation number, purchase history, refactoring older screens, the polish and theme passes.

Acceptance
- Through the REAL factory-built client with a fake transport: updatePurchaseShipping sends shippingStatus and trackingNumber "" to clear, a set value to set, and OMITS trackingNumber when unchanged; the response with trackingNumber null decodes and maps to an empty tracking number; a stored "" in a response also displays as empty; updatePurchase still sends notes only. Fixtures include the full meta object.
- The change type has a full truth table (original nil, "", value; edited empty, whitespace, same, different, over 100 characters), the Save enablement for status-only, tracking-only, both, and neither, and the request builders.
- The Shipping section clears a tracking number and shows it empty afterwards with Save disabled; the Notes section is unchanged.
- The mock behaves as the Decisions say.
- A delete whose screen was left before it completed still refreshes the item, items and list; a user switch or teardown mid-delete writes nothing; the item 404 path still drops the item.
- The stale comments listed in the I4b legacy-deletion report are corrected; no code behavior changes in that story.
- No change under contract/, .claude/, any .pbxproj, the synced Docs files, or LocalPackages/TrackerAPI beyond P0.

### The delete refresh defect (the root cause, with evidence)
1. `confirmDelete()` runs in an unstructured `Task` started by the Delete dialog button (ManagePurchaseView.swift:317). That task is NOT cancelled when the view goes away, so the delete itself completes and the model sets `finish = .deleted` (PurchaseDetailModel.swift:214).
2. The only consumer of `finish` is the view's `.onChange(of: model.finish)` (ManagePurchaseView.swift:78-80), which forwards to `onFinish`. When the user has already swiped back, `ManagePurchaseContent` is gone and the `onChange` never fires.
3. The refresh plan is launched ONLY by the host in `ItemDetailView.handlePurchaseDetailFinish` (ItemDetailView.swift:351-365) through `refreshRunner.run(steps)` in a `Task` (364). It runs only if the pushed view reported `finish`. So the refresh depends on the view being present. (This matches the I4b handoff's "Open risks".)
4. `PurchaseRefreshRunner` (ViewState/PurchaseRefreshRunner.swift:12-33) is `@MainActor`, runs the steps in order, never throws, and holds no session check of its own; the item and list services guard their own writes (generations) and ItemService handles an item 404 itself (drops the item and sets goneItemId; ItemDetailView:85-90 leaves the screen).
5. The ItemDetailView `.onDisappear` (95-101) deliberately keeps the item while a purchase detail is open (`openedPurchase == nil` guard); after the pop `openedPurchase` is nil and the item is cleared only when the item detail itself goes away.
Fix shape (Story C): the model runs the refresh itself after a successful or not-found delete, after setting `finish`, in the task that already runs `confirmDelete()` (it is not tied to the view), guarded by the purchase service's session (checked before each step). The host stops running the refresh for `.deleted` (it still closes the screen and still refreshes for `.gone`).

### Story A interface (all `nonisolated`, `Sendable`, `Equatable`; Foundation only)
1. `enum PurchaseTrackingChange { case unchanged; case set(String); case clear }` in PurchaseManagementUpdates.swift, with `static func derive(original: String?, edited: String) -> PurchaseTrackingChange`:
   - trimmedOriginal = original (nil is "") trimmed of whitespace and newlines; trimmedEdited = edited trimmed the same way.
   - trimmedOriginal empty and trimmedEdited empty: `.unchanged`.
   - trimmedOriginal non-empty and trimmedEdited empty: `.clear`.
   - otherwise trimmedEdited == trimmedOriginal: `.unchanged`; else `.set(trimmedEdited)`.
   - The 100-character limit is NOT applied here (a 101-unit edit still derives `.set(...)`); the section state blocks Save with `trackingTooLong`. Case is significant.
2. `PurchaseShippingUpdate` becomes `{ status: PurchaseShippingStatus, trackingChange: PurchaseTrackingChange }` (memberwise init `PurchaseShippingUpdate(status:trackingChange:)`), replacing the old `trackingNumber: String?` member (removed; no compatibility shim). `var wireTrackingNumber: String?`: `.unchanged` gives nil (the field is omitted), `.set(s)` gives s, `.clear` gives "" (never null). `static func make(originalStatus:originalTracking:editedStatus:editedTracking:) -> PurchaseShippingUpdate?` returns nil when `originalStatus == editedStatus` and the derived change is `.unchanged`; otherwise `PurchaseShippingUpdate(status: editedStatus, trackingChange: derived)` (the status is always the edited status, so a tracking-only edit still carries the current status).
3. `enum PurchaseEmptyValue` (or a static function on the existing types; the implementer picks the smallest placement and names it in the report) with `static func displayText(_ value: String?) -> String`: nil, "" and whitespace-only all give ""; any other value is returned UNCHANGED (not trimmed, so the user sees what the server stored). `PurchaseShippingSectionState.init(purchase:)` uses it for `draftTracking` and uses `purchase.trackingNumber` (raw) as the original for `derive` (derive already treats "" like nil). `PurchaseNotesSectionState.init(purchase:)` uses it for `draftText` (its change rules are untouched: notes behavior is unchanged).
4. `PurchaseShippingSectionState`: `update` is the new `PurchaseShippingUpdate?`; new `var trackingChange: PurchaseTrackingChange` (derived from the original and the draft); `canSave` stays `update != nil && !trackingTooLong`; `trackingTooLong` stays (trimmed draft over 100 UTF-16 units); `applying(_:)` resets from a returned purchase (so a returned null or "" tracking number gives an empty draft and, with the same status, `update == nil`, `canSave == false`).
5. `PurchaseNotesChange`, `PurchaseNotesUpdate` and `PurchaseNotesSectionState` keep their behavior and signatures exactly.

### Story C interface and behavior
1. **Shipping section.** `PurchaseDetailModel.saveShipping()` sends the update from the section state (Story A), which may now be a clear. Success updates the section from the RETURNED purchase (`applying`), so a cleared tracking number shows as an empty field and Save is disabled. The announcement is "Tracking number cleared." when the saved change was `.clear` (with or without a status change in the same save), otherwise "Shipping saved." as today. A failed save keeps the section's own scoped banner (Try Again repeats the same save, Dismiss clears it) and keeps the draft. `saveNotes()` and the Notes section are unchanged.
2. **Session accessor.** `PurchaseService` gains `var sessionGeneration: Int { generation }` (read-only; `generation` stays private and unchanged otherwise). It is the only service change.
3. **Runner guard.** `PurchaseRefreshRunner.run(_ steps: [PurchaseRefreshStep], while shouldContinue: @MainActor () -> Bool) async` (the existing `run(_:)` stays and calls the new one with an always-true check): before each step it asks `shouldContinue()` and stops (no further step) when it returns false. A failed step never throws and never stops the next step (unchanged).
4. **Model-owned delete refresh.** `PurchaseDetailModel` gains an optional refresh dependency passed at init (the implementer chooses the exact shape; the contract is behavioral): the model is given (a) a way to run refresh steps with a continue-check, built from the host's `PurchaseRefreshRunner`, and (b) a way to read the item service's current list id, because the plan needs `currentItemsListId` at the moment of the refresh. Both default to "do nothing" so existing call sites and previews compile; default-argument expressions are nonisolated, so MainActor values are built inside the init body. After `confirmDelete()` succeeds or answers not-found, in this order: clear the delete banner, announce, set `finish = .deleted`, then run `PurchaseRefreshPlan.stepsAfterDelete(itemId:listId:currentItemsListId:)` through the refresh dependency, in the same task that runs `confirmDelete()` (an unstructured task the Delete button starts; it is not cancelled when the view disappears), with the continue-check `service.sessionGeneration == capturedGeneration && !Task.isCancelled`, where `capturedGeneration` is read BEFORE the delete call. If the delete throws (CancellationError from a session end or user switch, or any other error), no refresh runs and nothing is written. The refresh never changes `finish`, never sets a banner, and never turns the delete into an error. A 404 on the item refetch is handled by `ItemService` (drops the item, sets goneItemId); the model adds nothing.
5. **Host.** `ManagePurchaseView` reads `itemService` and `listService` from the environment (as ItemDetailView does) and builds the refresh dependency for the model in `buildModelOnce()`. `ItemDetailView.handlePurchaseDetailFinish`: `.deleted` only closes the pushed screen (`openedPurchase = nil`) and does NOT run the plan (the model already does, once); `.gone` keeps today's behavior (close and run `PurchaseRefreshPlan.steps` in a task).
