# I3c: The archived-lists tab, and items on the generated client
Track: iOS. Depends on: I3a, I3b, I3b-2 (merged). Blocks: I4 (purchases).
Contract state: CONFORMANT at decisions revision 28. API models come only from the generated client.

Why: (1) Brian's use case is recording a purchase he forgot after a list was archived (decision L16): archiving closes list MANAGEMENT only; items, off-list items and purchases are still accepted and canCreateItem, canPurchase and canAddOffList do not depend on status. The app currently hides archived lists everywhere, which makes that impossible, so the lists screen gets an Active | Archived segmented control (mirroring the web) and archived lists open like any other list with the flags deciding what is shown. (2) Items still run on the hand-written network stack, whose models disagree with the server (the create request sends offList, which the server derives; no flags; purchase fields mapped by hand) and whose views and logs leak. This package moves the item operations onto the generated client, drives every item screen from the capability flags, and removes the leaks. (3) Brian's real-mode testing of I3b produced a UX polish backlog that he has deliberately banked for one pass after the functionality is complete; to keep that backlog from growing, the NEW code in this package follows four UI rules (below) and the OLDER screens are not refactored here.

Server facts (client guide, privacy matrix, decisions; confirm each against the synced files): see the guide sections named above. In short: the item type is derived by the server from the caller: an owner or co-owner (blind or not) adds a normal item (offList false), a MEMBER-role member adds an off-list (surprise) item (offList true); the create request carries no offList field. Edit and delete: a regular item by the owner or co-owner only (blind or not); a member's off-list item by its creator only (the owner and co-owner get 403); members and viewers cannot edit or delete regular items; PUBLIC non-members cannot write (403). PATCH /items/{id}/status is for non-blind owners and co-owners only. Reading: blind viewers (the recipient, or the owner or co-owner of a list whose recipient can log in), VIEWER-role members and PUBLIC non-members receive every item with status AVAILABLE, no updatedAt, no purchases, no off-list items, and no itemCount or purchasedCount on the list; everyone else sees real status, purchase summaries, and (canSeeOffList) off-list items. The capability flags canCreateItem, canSeeGiftActivity, canPurchase, canAddOffList and canSeeOffList are per list (ListSummary and ListDetail) and do not depend on the list status; the list MANAGEMENT flags (canEditList, canDeleteList, canManageMembers, canSetCoOwner) are false on an ARCHIVED list. GET /lists has an optional single status query (DRAFT, ACTIVE, ARCHIVED) and no default; DELETE /lists/{id} archives; an archived list rejects PATCH /lists/{id} with 422 CANNOT_EDIT_ARCHIVED_LIST. Money: request amounts have at most two decimals and at most 999999.99 (400 INVALID_PRICE otherwise); responses are JSON numbers with at most two decimals (convert with the package helpers; never arithmetic on a raw Double). Item fields to confirm from the generated schema: name, description, url, imageUrl, expectedUnitPrice, quantityRequested, priority, status, offList, createdBy, createdAt, updatedAt (optional), purchases summaries (optional), totalQuantityPurchased (optional).

Scope
1. Story A: the Active | Archived segmented control and the archived-list behavior.
2. Item domain models rebuilt from the generated types, one pure flag-derived ItemPermissions, pure view-state functions for every item screen.
3. GeneratedClientItemRepository (list, get, create, update, delete, and the status operation only if the existing UI offered it), a Mock with privacy scenarios, a session-safe ItemService with scoped errors; the hand-written item wire types and NetworkItemRepository deleted.
4. The item screens on flags: item list inside the list detail, item detail, add, edit, delete, built on the four UI rules, with the destructive color token and the inline error banner added to the design system.
5. Item-side log hygiene and the loose ends carried from the I3b handoff.

Decisions
- UI RULES FOR NEW CODE (from Brian's polish backlog; they apply to every NEW or REWRITTEN item screen and to the new design-system pieces; the older screens (children, members, profile, list screens other than what Story A edits, login, and so on) are NOT refactored in this package): (1) every confirmationDialog is attached to the control or row that triggers it, never to a List, ScrollView, Form, NavigationStack, or screen container (iOS 26 anchors a dialog to the view it is attached to); (2) errors are scoped: a mutation error (add, edit, delete an item) is thrown by the service to the initiating view and held in that view's local state (shown in the sheet or screen that started the action) and disappears on dismiss, retry success, closing the sheet, or leaving the screen; a load error is a separate property shown only on the screen whose load failed and cleared on a new load and on disappear; nothing is published in a shared service error that another screen reads; (3) destructive actions use role: .destructive AND an explicit tint of a new Color.destructiveColor token (system red, adapting to light and dark) that this package adds to DesignSystem/Colors; (4) one reusable InlineErrorBanner view with a pure InlineErrorBannerState, used by the new item screens: an icon (exclamationmark.triangle.fill in destructiveColor) and the message in a leading-aligned row with the text wrapping to full width, then a button row below with the actions left-aligned in a fixed order (primary "Try Again" when a retry exists, then "Dismiss" when dismissible), each button at least 44 points high, AppSpacing tokens, a tinted rounded background (destructiveColor at low opacity, the corner radius the other cards use), correct in light and dark, Dynamic Type friendly (buttons stack when they do not fit), the icon and message combined into one accessibility element, the buttons keeping their own labels, and a VoiceOver announcement when it appears. Where Story A edits an existing list screen (the Archive List action and confirmation), attach that confirmation dialog to its trigger button as well; do not otherwise restyle old screens.
- Archived lists (Story A): the lists service keeps ALL non-removed lists and exposes activeLists (status ACTIVE or DRAFT) and archivedLists (ARCHIVED); GET /lists is called without the status parameter. The lists screen has a segmented control at the top, "Active" (default) and "Archived", each segment with its own empty state ("No active lists" and "No archived lists"); the selection is view state for the session. An archived list shows an "Archived" badge, opens normally, and shows exactly what its flags allow (management controls are absent because those flags are false; items and purchases controls follow their own flags, which do not depend on status). Deleting a list is presented as ARCHIVING: the action label is "Archive List", the confirmation says the list moves to Archived, can no longer be edited, and items and purchases can still be recorded there; after a successful archive the lists are reloaded from the server (a fresh GET /lists, no local status synthesis) so the list appears under Archived with the server's flags. The I3b removal-sequence guard no longer records a removal for an archive (it still records leaves and gone-list drops). A 422 CANNOT_EDIT_ARCHIVED_LIST is NOT "list gone": show a plain message ("This list is archived and can't be edited."), do not leave the screen, and refetch the list detail so the flags refresh; ListErrorPresentation and the service change accordingly (name every changed existing test with this decision as the reason). loadListDetail still revalidates a cached detail; notFound and forbidden-with-cache still mean gone; an archived detail is shown normally.
- Item rights live in ONE pure function, ItemPermissions, derived from the list's capability flags, the item's offList and createdBy id, and the current user's id; no screen reads myRole. canAddItem = canCreateItem. A regular item (offList false) may be edited or deleted when canCreateItem is true and canAddOffList is false (owner or co-owner, blind or not). An off-list item may be edited or deleted only when item.createdBy.id equals the current user's id. canChangeStatus (only if the status operation is built) = canSeeGiftActivity and not canAddOffList. canSeeOffListItems = canSeeOffList (the server already omits them otherwise; the client also filters defensively). Status, purchase summaries, and progress show only when canSeeGiftActivity; when it is false every item shows as available with no status marker and no updatedAt, and nothing hints at hidden state. None of these depend on the list status. A comment cites the privacy matrix and the missing per-item flags (Brian has asked the API chat to consider canEdit and canDelete on ItemResponse; if the contract later adds them, ItemPermissions becomes a thin read of them).
- The add form: name (required), description, url, imageUrl, price, quantity, priority; no offList field anywhere; when canAddOffList is true the form shows one plain sentence that the item will be hidden from the recipient (a surprise item); price validation: at most two decimals, 0 to 999999.99, and Decimal through the package money helpers; quantity at least 1; priority within the generated schema's bounds.
- ItemService is session-safe like ListService (generation, cancellation, nothing written after the session ended, cleared at teardown, separate loading, mutating, and load-error state following UI rule 2), keeps its session clearable registration and the cached items per list (the cache is dropped when the list changes user or session), never logs an item id, name, url, price, or raw error, and handles 401 through the middleware and 403 ACCOUNT_DISABLED or 404 USER_NOT_FOUND through the existing session-ending seam. 404 on an item means gone (drop it and leave the screen); 403 shows a plain permission message; 422 maps per the documented responses; 429 rateLimited.
- Purchases are NOT part of this package: purchase screens and the old stack stay as they are and will not work against the real server until package I4; do not add, change, or remove purchase UI, and say so in the handoff. If an item row or detail currently offers a purchase action, leave it exactly as it is (and record in the handoff what it does in real mode).
- The pre-V1 idea "an off-list item bought on creation" needs an API decision first: build nothing for it, and leave only a code comment in the add form noting where it would go.

Non-goals: purchases, shipping, budgets, stats, history, link previews and image URL pre-population, item search, editing members or children, the version manager screen, refactoring older screens to the new UI rules (banked), the tab bar behavior and the theme pass (banked).

Acceptance
- Story A: the lists screen has the Active | Archived control with the behaviors above; an archived list opens, shows only what its flags allow, and still allows adding items when canCreateItem is true; archiving reloads the lists and the list appears under Archived; a 422 on edit shows the message and refreshes the flags and does not leave the screen; the changed existing tests are named with the decision.
- Through the REAL factory-built client with a fake transport, every documented response of the item operations maps (success, 400 with the validation message including INVALID_PRICE, 401, 403, 404, 422, 429, 500, undocumented, transport failure) with guide-accurate fixtures including the full meta object.

- Items for blind viewers, VIEWER-role members and PUBLIC non-members show no status marker, no purchase information, no updatedAt, and no off-list items anywhere (service, mapping, views), proven by tests; a view never shows or hints at hidden state.
- The create request never contains offList; money is Decimal end to end; a two-decimal and a three-decimal price are tested.
- Stale data from a previous session or user is impossible after teardown, a user switch, or cancellation (deterministic tests); the service never sets an error after the session ended.
- UI rules: Color.destructiveColor exists; InlineErrorBanner exists with the specified layout and is used by the new item screens; every destructive item action uses role: .destructive and the token; every confirmationDialog in the new or rewritten item screens and the Archive List dialog is attached to its trigger; an item mutation error never appears on another screen, and an item load error is cleared on a new load and on disappear (service and view-state tests); a narrow scanning test over Features/Items fails on a confirmationDialog attached to a List, ScrollView, Form, or NavigationStack, on a raw .red, and on a role: .destructive button without the token.
- No Log call in Features/Items or Features/Lists interpolates an id, name, email, url, price, or a raw error value (the scanning test covers Items and is extended to forbid interpolating raw error values in those folders).
- No change under contract/, .claude/, any .pbxproj, the synced Docs files, LocalPackages/TrackerAPI, or the purchase code.

# Deviations from the original brief (recorded by the Orchestrator)

D1. **The new item domain type is `ListItem`, not a rebuilt `GiftItem`** (Brian's answer, 2026-11-10, on the question "how do the purchase screens keep compiling untouched"). Reason: the purchase screens (`RecordPurchaseView`, `PurchaseHistoryView`, `PurchaseDetailView`, previews via `MockItemData`) take a `GiftItem`, and `RecordPurchaseView` formats `item.expectedUnitPrice` with `String(format: "%.2f", ...)`, which cannot compile against `Decimal`. Rebuilding `GiftItem` as the brief says would force an edit to a purchase file, which the brief forbids until I4. Conditions fixed by Brian:
1. The new domain type is named `ListItem` (Decimal? price, flag-driven fields, optional `updatedAt`, `purchases`, `totalQuantityPurchased`). Companion types: `ListItemPurchaseSummary` and `ListItemPerson` (final names set at Gate 1 of Story B).
2. The legacy `GiftItem` keeps its name, is trimmed to the members the purchase screens actually use, and carries a comment marking it LEGACY, to be deleted in I4. No purchase file is edited.
3. The bridge from `ListItem` to the legacy `GiftItem` lives next to the legacy type in Core/Models (not in a purchase file), converts the price with the TrackerAPI money helper, and is the only Double money path left in the app. It is marked LEGACY with the I4 deletion note and listed in the handoff.
4. A text-scanning test proves that no file outside the purchase folders, the legacy type's file, and the bridge references the legacy `GiftItem`, and that the new item services and item screens never use it.
5. The purchase entry point on the new item screens appears exactly when the list's `canPurchase` flag is true (no other logic) and opens the existing purchase screens through the bridge. Purchase UI is not changed. The handoff records what it does in real mode (the old stack, so it does not work against the real server until I4).
6. This epic's Story B text is updated accordingly (Gate 1 below).

D2. **Decision L16 is not present in the synced files.** `Docs/DECISIONS.md` (revision 28), `Docs/client-guide.md`, `Docs/error-codes.md`, `Docs/privacy-matrix.md` and `contract/openapi.json` contain no "L16" (searched). The brief cites L16 for "archiving closes list management only; items, off-list items and purchases are still accepted". What the synced files do say: the spec's `CapabilityFlags` (isRecipient, canSeeGiftActivity, canPurchase, canAddOffList, canSeeOffList, canCreateItem) have descriptions with no status dependency; the management flags are documented false on ARCHIVED (P23, guide 6.1); guide 6.1 says "Archived lists are read-only in the app" in the paragraph about the management actions table. Nothing in the synced files says whether the server accepts item writes on an archived list. Brian was asked how to treat this and did not answer that question; the Orchestrator proceeded on the recommended default: treat the brief as the decision, let the flags drive every control (so a server refusal shows as an ordinary item error), and verify against the real server in the handoff's real-mode step 3. If the server refuses, that is a contract-issues row, not a client workaround.

(3) create: the returned item is appended to `items` when `currentListId` matches and cached; update: the returned item replaces the matching entry in `items`, `currentItem` and the cache; delete: the item is removed from `items`, `currentItem` and the cache on success. (4) 404 on update, delete or detail load means the item is gone: it is removed from `items`/`currentItem`/cache, `goneItemId` is set to its id, and the typed `.notFound` is thrown (mutations) or set as `loadError` (detail load); `goneItemId` is cleared only by `clearForSession()`. (5) Session safety exactly like ListService: a generation counter captured before the first await by every operation; after `clearForSession()` (teardown or user switch) an in-flight operation writes NOTHING, sets no error and (for mutations) throws `CancellationError`; `Task` cancellation sets no `loadError`; loading flags are only reset by the same generation; `clearForSession()` empties `items`, `currentItem`, `currentListId`, `loadError`, `goneItemId`, the mutation counter, and the cache. (6) No Log call interpolates an item id, name, url, price or raw error (counts and constants only); manual Sentry spans with the explaining comment on the MainActor async/throws functions like ListService. (7) Removed: `error`, `isLoading`, `showPurchased`, `showOffList`, `filteredItems`, `purchasedItems`, `availableItems`, `partialItems`, `notiftyPurchaseChase`, `refreshItem` (the dead helpers are unused; confirm by grep).
