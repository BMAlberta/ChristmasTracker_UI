# UX1a: One error and stale-data policy for every screen
Track: iOS. Depends on: I4c (merged). Blocks: UX1b (dialogs, destructive colors, tab bar, Face ID hint), the theme pass.
Contract state: unchanged; no contract change in this package.

Why: Brian's real-mode testing produced four findings about how errors show, and the newest screens (items, purchases, the Children delete) already follow the target pattern while the older ones do not: (1) every screen builds its own error row, so the buttons and layout differ; (2) a shared service error is read by several screens, so a failed add-member error is still shown on the lists screen after navigating back; (3) when a list's detail refresh and its items refresh both fail, two banners show the same problem; (4) screens open cache-first and ignore a failed revalidation, so an unreachable server shows nothing until the user pulls to refresh, and stale data is shown as if it were current.

Policy (the product decisions; Brian approved them as the banked polish backlog items 2, 3, 8 and 9):
- ONE component: every error on every screen is an InlineErrorBanner (an icon and the message in a leading row, then left-aligned Try Again and Dismiss buttons, at least 44 points high, tokens only). No ad-hoc error rows, labels or alerts for errors remain (the full-screen ErrorStateView stays only for a screen that has NOTHING to show and cannot load).
- SCOPED errors: a MUTATION error (create, update, archive, add or remove a member, leave, set a co-owner, any save) is THROWN by the service to the initiating view and held in that view's local state, shown inside the screen or sheet that started the action; it disappears on dismiss, on a successful retry, on closing the sheet, and on leaving the screen. A LOAD error is a separate property of the service scoped to ONE screen, cleared when that screen starts a new load and when it disappears. Nothing is published in a shared error property that any other screen reads. A screen never shows an error produced by another screen's action.
- STALE-DATA HONESTY: a screen that opens from cache and revalidates in the background shows, when the revalidation fails, ONE banner: "Couldn't update. Showing saved data." with Try Again and Dismiss; the cached data stays visible. A screen with NO cached data that fails to load shows the full error state with Try Again. A pull to refresh that fails shows the same banner. Try Again repeats the failed work (a forced fetch). A failed revalidation caused by a gone resource (404) or a session end keeps its existing behavior (leave the screen, or the sign-in flow takes over); a 403 or 404 is never shown as "Couldn't update".
- ONE banner per screen for connectivity: when the failures of one screen are the SAME category (network unreachable, timeout, or server error), show a single banner at the top with a single Try Again that retries all the failed loads of that screen; when the categories differ, show one banner per distinct category (at most two). The list detail screen is the main case: its detail refresh and its items refresh fail together today and show twice.

Scope: the lists dashboard, the list detail screen (header, items section, members section), create list, edit list, the Members add, remove and leave flows, the Children screen's load error row, the Profile screen's error handling, and the item screens (their load errors adopt the stale-data and one-banner policy; their mutation errors already conform). ALSO IN SCOPE, from the I5a review: (a) the Statistics screen and the budget editor adopt the same policy (their banners already use InlineErrorBanner; make their stale-data and one-banner behavior come from LoadFailurePolicy, and fix finding C: a stats load that finishes after the screen disappeared must not set a failure, and a failed load of the previous year must not show a stale banner on the newly selected year); (b) finding D: ListService.loadLists must NOT return at once when a load is already in flight; it must wait for that load's result, so the budget editor's person picker never shows "Nobody to add yet" while the lists are still loading (add a test: opening the editor while a lists load is in flight shows the loading state, then the people); (c) finding A: when the stats response shows a budget but the budget cache lacks that year, Edit Budget and Duplicate must load the budget first (or show the banner with Try Again) instead of doing nothing; (d) finding E: the budget editor's list load must not write a shared error that the Lists screen reads (this follows from removing the shared ListService error); (e) finding B: after a successful delete, if the follow-up stats refresh fails, the stats cache must not keep showing the deleted budget (drop the budget block for that year locally on a successful delete). Login, registration and lock screens keep their own alert or inline error patterns and are NOT changed.

Non-goals: confirmation dialogs and anchoring, destructive colors, the tab bar, the Face ID hint, the Children Try Again confirmation (all UX1b), the theme pass, any contract or repository change, purchases (already conforming), new screens.

Decisions
- A pure, nonisolated, Sendable LoadFailurePolicy (name may vary) is the single source of truth for what a screen shows after a failed load: inputs are whether cached data is shown and the list of failures (each with a category: unreachable, timeout, server, rateLimited, forbidden, notFound, sessionEnded, other); outputs are none, a stale-data banner, a merged banner, up to two banners, a full error state, or a leave-the-screen or sign-in-flow-takes-over instruction. It also owns the banner texts ("Couldn't update. Showing saved data." for a failed revalidation with cached data; the existing plain messages otherwise; the rate-limit message keeps its retry hint). Views never decide this; they render the policy output.
- Services expose, per screen, a small observable failure value (or a throwing method for mutations) instead of a shared error: for example ListService.listsLoadFailure (dashboard), detailLoadFailure and detailRefreshFailure (list detail), ItemService.listLoadError (already separate) and detailLoadError, ChildService.loadFailure. Each is set only by the load that belongs to that screen, cleared at the start of that load and at teardown, and cleared by the screen's disappear handler. Remove the shared `error` property (and clearError) from every service that has one once no view reads it; if a property must stay for compatibility, it is no longer read by any view and a scan test proves it.
- Cache-first with honest revalidation: where a service already revalidates a cached value in the background (ListService.loadListDetail), a revalidation failure is RECORDED in the screen's failure value (not swallowed) when cached data is being shown. Where loadItems and loadLists serve a fresh cache without fetching (inside the cache window), no revalidation happens and no failure is possible: do not add network calls just to show errors; a screen that has just opened from a fresh cache shows nothing, and pull to refresh forces the fetch as today. Keep every session-safety guarantee (generation checks, cancellation at teardown, nothing written after the session ended).
- Mutation errors in older screens move to the throw-and-hold pattern exactly like the purchase screens: the service method throws a typed error and publishes nothing; the initiating view holds it in local state and shows an InlineErrorBanner inside the sheet or section. Success clears it.
- No error text includes server data beyond the documented message; nothing about lists, names, or ids is logged.

Acceptance
- LoadFailurePolicy has a full truth table: cached or not; one failure of each category; two failures of the same category (one merged banner); two of different categories (two banners); a gone resource; a session end; a stale-data banner only when cached data is shown; Try Again targets (which loads it repeats).
- Every screen in Scope renders only InlineErrorBanner for errors; a scan test fails on an ad-hoc error row pattern (a Label with the exclamationmark.triangle.fill icon built outside InlineErrorBanner, an alert showing an error message, or a view reading a service's shared error) in the Scope folders, with a documented allowlist.
- A failed add-member (or any older mutation) error is shown only inside its sheet or section and never on another screen (service and view-state tests, and the scan that no view reads a shared error); no service has a shared published error read by a view.
- The list detail screen shows ONE banner when its detail refresh and items refresh fail for the same category, with a Try Again that retries both; two banners only when categories differ.
- A revalidation failure with cached data shows "Couldn't update. Showing saved data."; a fresh-cache open shows nothing; a load with no cache shows the full error state; 404 and session end keep their behavior; a 403 or 404 never shows "Couldn't update".
- Session safety and stale-data guarantees unchanged (deterministic tests).
- No change under contract/, .claude/, any .pbxproj, the synced Docs files, LocalPackages/, authentication, repositories, or the purchase screens' behavior.

# Gate 1 specs

## Story U1: the pure policy (Gate 1)
- Contract slice: none. Interface introduced: yes (pure types only; no UI, no service).
- Files (new): APP/Features/Shared/ErrorPolicy/LoadFailurePolicy.swift (policy, outputs, texts), LoadFailureCategory.swift (category, source, classification from ListError, ItemError, ChildError, BudgetError). If Features/Shared does not exist, the implementer uses the folder that holds the other cross-feature view-state types and says so. Tests: TESTS/Features/Shared/LoadFailurePolicy*Tests.swift.
- Interface (all `nonisolated`, `Sendable`, `Equatable`):
  - `enum LoadFailureCategory { unreachable, timeout, server, rateLimited, forbidden, notFound, sessionEnded, other }`.
  - `enum LoadSource { lists, listDetail, items, itemDetail, children, stats, budgets, people }` (what Try Again repeats).
  - `struct LoadFailure { category; source; retryAfter: Int? }`, with classifiers `LoadFailure(_ error: ListError, source:)`, `(ItemError ...)`, `(ChildError ...)`, `(BudgetError ...)`. Every enum case is mapped by an exhaustive switch with no `default`. Mapping: network -> unreachable (no typed error reports a timeout, so `timeout` is reachable only through the policy inputs; documented); server and invalidResponse -> server; rateLimited -> rateLimited; forbidden -> forbidden; notFound, childNotFound -> notFound; sessionEnded and unauthorized -> sessionEnded; all validation and domain cases (recipientNotFound, duplicateRecipientYear, archivedReadOnly, validation, memberEmailNotFound, alreadyMember, membershipNotFound, invalidPrice, cannotDeleteWithPurchases, childHasLists, alreadyExists, sumExceedsTotal, hasPurchases) -> other.
  - `struct LoadBanner { state: InlineErrorBannerState-compatible message; retryTargets: [LoadSource] }` (message plus which sources Try Again repeats).
  - `enum LoadFailureOutcome { none; staleData(LoadBanner); merged(LoadBanner); banners([LoadBanner]) (2 max); fullError(LoadBanner); leaveScreen; signInTakesOver }`.
  - `enum LoadFailurePolicy { static func outcome(hasCachedData: Bool, failures: [LoadFailure]) -> LoadFailureOutcome }` and `static let staleDataText = "Couldn't update. Showing saved data."`.
- Exact definitions (amended before the tests were written; the existing code never leaves a screen on forbidden, it shows the plain message, so the policy keeps that):
  - `LoadFailure` also carries `plainMessage: String`, copied from the typed error's `userMessage` at classification (so rate-limit keeps its retry hint, validation keeps its server message). `LoadBanner` is `struct { message: String; retryTargets: [LoadSource] }`.
  - Connectivity categories: unreachable, timeout, server.
  - Evaluation order: (1) no failures -> `none`. (2) any `sessionEnded` -> `signInTakesOver`. (3) any `notFound` -> `leaveScreen`. (4) group the rest by category; groups are ordered by category priority unreachable, timeout, server, rateLimited, forbidden, other. A group's retryTargets are its sources, deduplicated, in order of first appearance. A group's message is `staleDataText` when `hasCachedData` and the category is a connectivity category, else the plain message of its first failure.
  - One group: with cache and connectivity -> `staleData(banner)` when it has exactly one distinct source, `merged(banner)` when it has more than one (same stale text, one Try Again for all). With cache and not connectivity (rateLimited, forbidden, other) -> `banners([banner])` (plain message, never the stale text). Without cache -> `fullError(banner)` (retry targets merged).
  - Two or more groups (any cache state) -> `banners([...])` with at most two: the first two groups by priority; the retry targets of any further groups are appended (deduplicated) to the second banner, so Try Again still repeats every failed load. Documented tie-break.
  - forbidden is never stale text. `timeout` is produced by no typed error today; it is reachable through the policy inputs and tested directly.
- Acceptance tests (U1): the full truth table (cached/not x each category x one/two same/two different); every case of ListError, ItemError, ChildError and BudgetError mapped; texts; 403/404 never stale; session end and gone resource instructions; Try Again targets deduplicated and ordered; more than two categories collapse to two (documented tie-break).
- Out of scope in U1: services, views, any change to existing files.

### Story U2: exact interface (amendment written before the U2 tests; it supersedes any looser wording above)
ListService:
- Remove `error` and its writer. `private func record` becomes a pure classifier plus the operation-name log (it returns the typed ListError, or nil for cancellation and for a stale generation) and stores nothing.
- New observable state: `private(set) var listsLoadFailure: ListError?` and `private(set) var detailLoadFailure: ListError?`, with `func clearListsLoadFailure()` and `func clearDetailLoadFailure()`. Both are cleared in resetSession (clearForSession and clearCache).
- `@discardableResult func loadLists(reportingFailure: Bool = true) async -> ListError?` and `@discardableResult func refreshLists() async -> ListError?` (the existing in-line revalidation inside loadLists uses the same private path). The return value is the failure of the fetch that this call performed or waited for (nil on success, cancellation or a session that ended). When `reportingFailure` is true the failure is also stored in `listsLoadFailure` (cleared when a lists load or refresh STARTS); when false it is stored nowhere (used by the budget editor's person picker: it never writes a value another screen reads). `refreshLists()` always reports.
- Finding D: when `loadLists` is called while a lists load is already in flight, it WAITS for that load to finish and returns that load's result without a second fetch (a waiter caller that passes `reportingFailure: false` does not store, but the in-flight load stores according to its own flag). A teardown or user switch resumes every waiter with nil, and nothing is written for the old session. No real sleep or yield loop: use a continuation list or the in-flight task, resumed from the load's completion path.
- `loadListDetail` records `detailLoadFailure` for any failure of the detail load (a revalidation failure while cached data is shown, a failure with no cache, and the guarded not-found); it clears it when a detail load starts. A forbidden or not-found keeps its existing drop/gone behavior (goneListId) in addition. `refreshListDetail` is unchanged (it returns its failure and stores nothing).
- All mutations (createList, updateList, removeCoOwner, deleteList, addMember, removeMember, leaveList, setCoOwner) throw the typed ListError (CancellationError for a cancelled call or an ended session) and store nothing. A follow-up reload or refetch that fails AFTER the mutation succeeded (the lists reload after an archive, the detail refetch after an archive, the detail refetch after adding or removing a member) is logged by operation name only and published nowhere; the mutation returns normally (declared deviation: the next load shows an honest failure).
ChildService: remove `error`; the add and delete failures are only thrown. `phase` stays the Children load channel. Add `func clearLoadFailure()` which turns a `.failed` phase into `.idle` and does nothing otherwise (it never clears a loaded list).
StatsService/BudgetService: new `nonisolated struct StatsLoadFailure: Equatable, Sendable { let year: Int; let error: BudgetError }`; `private(set) var loadFailure: StatsLoadFailure?` replaces the BudgetError-typed property (still the ONLY stored property named *Error*/*Failure*); `func failure(forYear year: Int) -> BudgetError?` returns the stored error only for that year; `clearLoadFailure()` stays; a load that was cancelled records nothing; `func dropBudget(year: Int)` removes the budget block of that year from the cached stats locally (no network, no-op when absent or when the session changed, bumps no generation).
StatsScreenModel (finding C, A, B at model level): the banner/error it exposes for the selected year comes from `statsService.failure(forYear: selectedYear)`, so a failure of another year never appears on the selected year; the model owns its in-flight load task(s), `onDisappear()` cancels them and clears the failure, and a load that completes after disappear sets nothing; after a successful delete it calls `statsService.dropBudget(year:)` before the follow-up refresh; Edit Budget and Duplicate, when the budget cache lacks the year, first call `budgetService.loadBudgets(force: true)`: on success it opens the sheet, on failure it sets `budgetCardBanner` to a retryable banner and the Try Again action repeats the same step. BudgetEditorModel uses `listService.loadLists(reportingFailure: false)` and its return value, never a shared property.

### Story U3: exact interface (amendment written before the U3 tests)
Shared pure layer (Features/Shared/ErrorPolicy/, all `nonisolated`, `Sendable`, `Equatable`):
- `LoadBannerPresentation.state(for banner: LoadBanner, dismissible: Bool = true) -> InlineErrorBannerState`: message from the banner (a blank message falls back to InlineErrorBannerState's fallback text), actions `[.tryAgain, .dismiss]` (no `.dismiss` when `dismissible` is false).
- `ScreenLoadPresentation`: `struct { let banners: [LoadBanner]; let fullError: LoadBanner?; let leavesScreen: Bool; let signInTakesOver: Bool }` with `static func make(hasCachedData: Bool, failures: [LoadFailure]) -> ScreenLoadPresentation` mapping `LoadFailurePolicy.outcome` (staleData and merged -> one banner; banners -> up to two; fullError -> fullError; leaveScreen -> leavesScreen; signInTakesOver -> signInTakesOver; none -> everything empty). Dismissal is applied BEFORE the call: a screen filters out the failures the user dismissed (a `DismissedLoads` helper: `struct DismissedLoads { mutating func dismiss(_ sources: [LoadSource]); mutating func reset(); func visible(_ failures: [LoadFailure]) -> [LoadFailure] }`, a failure of a dismissed SOURCE is hidden until its source's next load starts and `reset(source)` is called).
Per-screen pure view states (each owns the mapping from the service values to failures, and the Try Again targets):
- `DashboardLoadState.make(hasCachedLists: Bool, listsFailure: ListError?, archiveFailure: ListError?, dismissed:)`: the lists failure goes through the policy with source `.lists`; the archive failure is a MUTATION error and is NOT part of the load presentation (it is shown as its own local InlineErrorBanner, `MutationBanner.state(for: ListError) -> InlineErrorBannerState?`, nil for sessionEnded/cancellation).
