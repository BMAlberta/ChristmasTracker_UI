# I4b: Managing your own purchase, an unconfirmed purchase, and deleting the legacy purchase stack
Track: iOS. Depends on: I4a (merged) and the contract sync on this branch (decisions revision 33: S14). Blocks: nothing (build 2 adds purchase history, stats and budgets screens).
Contract state: CONFORMANT. API models come only from the generated client.

Why: (1) After I4a a buyer can record a purchase but cannot see it in detail, set its shipping status, add notes, or undo it. Decision S14 added DELETE /tracker/v2/purchases/{id} (operationId deletePurchase). (2) The server does not de-duplicate purchases: two identical requests create two purchases. If a record request reaches the server but the response is lost (a timeout or a dropped connection), the app shows an error and a retry would silently record the purchase twice, distorting the item status and the buyer's budget. (3) The old hand-written purchase stack (legacy Purchase types with Double money, PurchaseHistoryView, PurchaseDetailView, PurchaseEditView, PurchaseRow, the legacy PurchaseRepository and its network and mock implementations, GiftItem, MockItemData, and Core/Networking) is dead code that is no longer reachable from any screen and carries raw-error log lines; it must go.

Server facts (client guide, privacy matrix, decisions S13, S14, P11, P24, C13, L16; confirm each against the synced files):
- DELETE /tracker/v2/purchases/{id} (deletePurchase): bearer, no body. Only the purchaser may delete; anyone else (owner, co-owner, another member, a stranger) gets 404 PURCHASE_NOT_FOUND, identical to a nonexistent id (P11). 400 for a malformed id, plus the usual 401, 403 (ACCOUNT_DISABLED), 429 and 500. The 200 response is the DELETED purchase in the same Purchase shape as GET /purchases/{id} (including item {id, name, listId}); it is not the updated item, because the delete must work even when the purchaser can no longer see the item. It is a hard delete in one transaction: the purchase is gone from GET /purchases and GET /purchases/{id} returns 404; the item status is recomputed from the remaining purchases (0 gives AVAILABLE, below quantityRequested gives PARTIAL, at or above gives PURCHASED) except that a WRAPPED or GIFTED item keeps its status (S13); quantityPurchased and quantityRemaining follow; the buyer's recorded spend drops, so the next budget check already sees it. A second DELETE of the same id returns 404 PURCHASE_NOT_FOUND, also for a concurrent double delete. It works on archived lists (L16) and on soft-deleted items. After a delete the client REFETCHES the item or the list items exactly as after creating a purchase; if the item refetch returns 404 the item is no longer visible to the user: drop it from the caches and leave the item screen.
- Immutability: a purchase's core fields (quantity, totalCost, item, recipient, store name, confirmation number) are immutable after creation. To correct a quantity or cost the buyer deletes the purchase and records a new one (which runs the budget confirmation again). PATCH /purchases/{id} (updatePurchase) accepts ONLY notes (up to 1000 characters) and trackingNumber (up to 100), both optional; an empty {} body is valid and returns 200 with the current purchase (do not rely on updatedAt moving); to CLEAR notes send an empty string ("") because null is a 400; the generated request type has no quantity or totalCost fields. Shipping changes go through PATCH /purchases/{id}/shipping (updatePurchaseShipping): shippingStatus is required (NOT_TRACKED, NOT_SHIPPED, SHIPPED, DELIVERED; any change between states is allowed; a new purchase starts as NOT_TRACKED) and trackingNumber is optional (up to 100). GET /purchases/{id} (getPurchase) and GET /purchases (listPurchases, which returns only YOUR OWN purchases, T3) exist. Confirm from the guide and spec whether a trackingNumber can be cleared and how; if the contract is silent, treat an empty tracking field as "unchanged" (never send an empty string for it), and put the question in the handoff.
- Who sees what: purchase information on items (summaries, status, quantities) is visible only to callers with canSeeGiftActivity; blind owners and co-owners, viewer-role members and PUBLIC non-members never see purchases. The purchaser of a purchase is shown to the callers who can see it; managing a purchase (open its detail, change shipping or notes, delete) is for the purchaser only: decide ownership from purchase.purchaser.id (or the summary's purchaser id) equal to the signed-in user's id, never from a role.
- The server does not de-duplicate: POST /items/{itemId}/purchases answers only 200 (confirmation_required), 201, 400, 401, 403, 404, 429, 500; it never returns 409 or 422; two concurrent identical creates both return 201.

Scope
1. Story P0: regenerate from the synced contract (one new operation).
2. Story A: domain types and pure rules for managing a purchase (shipping status, update inputs, ownership, the detail view state) and the pure classification of an unconfirmed record request.
3. Story B: the repository, service and mock for get, update, shipping update and delete; session-safe.
4. Story C: the purchase detail screen, the item detail integration (own purchases open it, other purchases are read-only rows), and the unconfirmed-purchase handling on the Record Purchase screen.
5. Story D: delete the legacy purchase stack and Core/Networking where nothing live uses it, rename RecordPurchaseError to PurchaseError, and finish the log hygiene.
6. Story E: handoff and the real-mode check.

Decisions
- UI RULES FOR NEW CODE (banked polish backlog; they apply to everything new or rewritten in this package; older screens are not refactored): (1) every confirmationDialog is attached to the control that triggers it, never to a List, ScrollView, Form, NavigationStack, or screen container; (2) errors are scoped: a mutation error is thrown to the initiating view and held in its local state (an InlineErrorBanner inside that screen or section) and disappears on dismiss, retry success, or leaving the screen; a load error is its own property, cleared on a new load and on disappear; nothing is published in a shared service error that another screen reads; (3) destructive actions use role: .destructive with Color.destructiveColor; (4) errors use the existing InlineErrorBanner (no alerts for errors).
- Names: RecordedPurchase (from I4a) is the full purchase. Add PurchaseShippingStatus (the four generated values), PurchaseNotesChange (unchanged, set(String), clear), PurchaseNotesUpdate and PurchaseShippingUpdate (input values), and PurchaseManagementError (typed errors for get, update, shipping and delete, with plain messages). Money stays Decimal. After Story D, RecordPurchaseError is renamed PurchaseError (the legacy name is free once the legacy file is deleted).
- Ownership: a pure function (for example PurchasePermissions.canManage(purchasePurchaserId:currentUserId:)) is the ONLY place that decides whether a purchase can be opened for management; it compares ids, never roles. The item detail's purchase card shows every purchase the caller may see (existing behavior); rows the caller owns are tappable (a chevron, an accessibility hint "Opens your purchase") and open the purchase detail; all other rows are read-only (no chevron, no action). If the purchase summary on the item does not carry the purchase id and the purchaser id, determine own purchases in the smallest sound way (for example listPurchases filtered by the item, which returns only your own purchases) and report the choice; never open another user's purchase.
- The purchase detail screen (PurchaseDetailView, new): loads the purchase through getPurchase (a load error banner local to the screen with Try Again and Dismiss; 404 means gone: close the screen and refresh the item). It shows the immutable core fields read-only (item name, quantity, total cost formatted from Decimal, store, purchase date, confirmation number if present) with one plain sentence: "To change the quantity or cost, delete this purchase and record it again." It has two separate sections, each with its own Save and its own scoped error banner: Shipping (a status picker of the four values and a tracking number field, saved through updatePurchaseShipping; Save enabled only when something changed; the tracking number field is edited ONLY here) and Notes (a text field up to 1000 characters, saved through updatePurchase with the notes only; clearing the field sends an empty string; Save enabled only when the text changed; the UI never sends trackingNumber to updatePurchase). After a successful save the screen updates from the RETURNED purchase (no refetch of the item is needed because the item status cannot change). A destructive Delete button (role .destructive, Color.destructiveColor) with ONE confirmationDialog attached to that button: title "Delete this purchase?", message "It will be removed from this item and from your budget, and the remaining quantity will update. This can't be undone.", destructive button "Delete Purchase". On success the screen closes and the item detail, the items and the list detail are refreshed with the I4a refresh plan (a pure function); a 404 on delete (already removed) is treated as deleted (close and refresh); a 404 from the item refetch drops the item from the caches and leaves the item screen. A failed refresh never turns a successful delete into an error. Archived lists behave exactly the same (the flags and ownership decide).
- Unconfirmed purchase handling (Record Purchase screen): when the record request fails with NO HTTP response, classify the failure with a pure function over the underlying URL error code: DEFINITELY-NOT-SENT (cannot connect to host, cannot find host, DNS failure, not connected to the internet, secure connection failed before a request, data not allowed, roaming off, call active, and any failure the client raised before sending) keeps today's behavior (the banner with Try Again and Dismiss); UNCONFIRMED (timed out, network connection lost, bad server response, cannot parse response, zero-byte resource, or any URL error you cannot place with certainty) means the server may have recorded the purchase. For an UNCONFIRMED failure the form shows an InlineErrorBanner with the message "We couldn't confirm whether this purchase was recorded." and exactly two actions: "Check Item" (closes the form and force-refreshes the item detail, the items and the list detail, so the user can see whether the purchase is there) and "Record Again" (a new submit from editing, with no token, subject to the budget confirmation as always) plus Dismiss; there is never an automatic retry. This applies to a first submit and to a confirmed resubmit (after Record Anyway). HTTP errors with a response (400, 403, 404, 429, 500, undocumented) are definitive and keep their existing handling. When you are unsure, classify as UNCONFIRMED. Extend the typed error and the state machine minimally and keep every I4a rule (no token reuse, nothing automatic, the token never stored).
- Legacy deletion (Story D): delete only what the inventory proves is unreferenced by live code (live code means anything reachable from the app target's composition root, screens, services, and the tests that cover live code): the legacy Purchase, ShippingStatus, CreatePurchaseRequest and warning types in Core/Models/Purchase.swift, GiftItem, MockItemData, PurchaseHistoryView, PurchaseDetailView (the legacy one; the new screen has its own name or location: pick distinct names so the deletion is unambiguous), PurchaseEditView, PurchaseRow, the legacy PurchaseRepository protocol, NetworkPurchaseRepository, MockPurchaseRepository, and the files in Core/Networking that nothing live uses (NetworkAPIClient, MockAPIClient, and anything else with no live reference). If something in Core/Networking or the legacy files IS still used by live code, KEEP it, and list it in the handoff with its users and the reason. Previews and tests that used GiftItem or MockItemData are rewritten on ListItem fixtures (or deleted when they only tested the deleted code; name each with the reason and where equivalent coverage lives). Remove the composition root's construction of the legacy network client and legacy purchase repository. Then rename RecordPurchaseError to PurchaseError everywhere. All raw-error log lines in the deleted files go with them; sweep the remaining Features/Purchases folder for any log call that interpolates an id, name, amount, or raw error.
- Mock mode: the mock purchase management behaves like the server (own purchases only, immutability, shipping and notes updates, delete drops the purchase, a second delete returns not-found); it does not move mock item counts or statuses (documented limitation), and no test may assume it does.
- Session safety: the purchase management service is session-safe like the other services (generation, cancellation, nothing written after the session ended, cleared at teardown through the existing SessionClearable registration; the production-wiring test pins the clearable count with a stated reason); methods throw typed errors and publish nothing in a shared property; no purchase data, notes, tracking numbers, or amounts are logged.
- Hermetic tests, no stale data after teardown or a user switch, no real sleeps.

Non-goals: purchase history, stats and budgets screens (build 2), editing quantity, cost, store name, or confirmation number (not allowed), any other user's purchase, an idempotency key (a possible contract proposal), refactoring older screens, the tab bar and theme passes (banked).

Acceptance
- Through the REAL factory-built client with a fake transport: getPurchase, updatePurchase, updatePurchaseShipping and deletePurchase map every documented response (200, 400, 401, 403, 404 PURCHASE_NOT_FOUND, 429, 500, undocumented, transport failure) with guide-accurate fixtures including the full meta object and the purchase shape with item {id, name, listId}; the update request carries only the fields the user changed (notes only, never trackingNumber from the notes save; a notes clear sends an empty string); the shipping request carries shippingStatus and, when changed, trackingNumber; delete sends no body; the deleted purchase decodes.
- Ownership and visibility: only the purchaser's rows open the detail; blind owners, blind co-owners, viewer-role members and PUBLIC non-members never see purchase rows; another user's purchase is never openable (view-state tests for every persona, on active and archived lists).
- The detail screen: core fields read-only with the sentence; two independent sections with their own Save, enabled only on change; scoped errors; the delete confirmation attached to the Delete button, destructive and red; after delete the refresh plan runs, a 404 on delete counts as deleted, a 404 on the item refetch drops the item.
- Unconfirmed failures: the classification table is complete and tested for every URL error code you handle plus the unknown default (UNCONFIRMED); the banner offers Check Item and Record Again (never an automatic retry); definitive failures keep Try Again; a token is never reused; Check Item closes the form and force-refreshes.
- The legacy stack is gone except what the inventory proves is live (listed in the handoff with reasons); the app builds, links and runs; no test or preview references a deleted type; RecordPurchaseError is renamed PurchaseError; no log call in Features/Purchases interpolates an id, name, amount, note, tracking number or raw error.
- No change under contract/, .claude/, any .pbxproj, the synced Docs files, or LocalPackages/TrackerAPI beyond P0.

### Facts that matter, with evidence
- **The Purchase payload** (spec 773-883): id, itemId, quantity, totalCost (Money), storeName?, notes?, confirmationNumber?, trackingNumber? (all nullable strings), shippingStatus, shippedAt?, deliveredAt?, purchaser (PersonRef), recipient (PersonRef), item {id, name, listId}, purchasedAt, createdAt, updatedAt. The domain `RecordedPurchase` (Features/Purchases/Domain/RecordedPurchase.swift:19-36) carries everything EXCEPT the item reference (name, listId); Story A adds it.
- **Doc inconsistency (not a code issue): the guide says the delete response "does not include the item"** (Docs/client-guide.md:673), while the spec and the brief say the deleted purchase has the same shape as GET /purchases/{id}, which includes item {id, name, listId} (spec 850-870, deletePurchase 200 refs Purchase). The client decodes the spec shape and does not depend on the item being present beyond what the schema requires; this goes in the handoff as a guide wording issue for the API team.
- **Doc inconsistency: the getPurchase description says "purchaser or list owner only"** (spec 4424) while S14 and P11 say only the purchaser sees a purchase through the purchase endpoints. The client treats every non-purchaser as 404 and never opens another user's purchase; recorded in the handoff.
- **Clearing trackingNumber: the contract is silent.** The guide's 7.7 (Docs/client-guide.md:684-695) shows only a set; the spec types trackingNumber as `string` with maxLength 100 (no null, no clear semantics) for updatePurchase and updatePurchaseShipping. The brief's rule applies: an empty tracking field means "unchanged", never an empty string; the question goes in the handoff.
- **The purchase summary on items carries the purchase id and the purchaser.** `ListItemPurchaseSummary` (Core/Models/ListItem.swift:18-24) has id, quantity, totalCost, purchaser (ListItemPerson with id and displayName) and purchasedAt; the spec's PurchaseSummary (885-918) also carries shippingStatus.
