# I3d: Deleting a child by archiving their active lists, and the Members section fix
Track: iOS. Depends on: I3c, I4a and I4b (merged; the contract at decisions revision 33 is already synced on master). Blocks: nothing.
Contract state: CONFORMANT. API models come only from the generated client.

Why: (1) Decision L17 changed the child deletion rule: DELETE /users/me/children/{id} succeeds when none of the child's lists is ACTIVE or DRAFT (archived lists no longer block); otherwise it returns 422 CANNOT_DELETE_RESOURCE with the message "Cannot delete child with active lists; archive them first". "Archive each active list, then delete the child" is a CLIENT flow after a confirmation, not a server cascade. Today the Children screen says "This child still has lists ... Delete those lists first", which is now wrong, and offers no way to do it. (2) The client guide now says ListDetail.members NEVER contains the owner, co-owner, or recipient (read owner, coOwner and recipient, then members) and memberCount counts only ACTIVE members and viewers. The Members section shows only the roster, so it never shows who owns the list.

Server facts (client guide, privacy matrix, decisions; confirm each against the synced files): after a child is deleted, the child leaves GET /users/me/children and POST /lists for that child returns 404 RECIPIENT_NOT_FOUND; the owner, co-owner and members of the child's ARCHIVED lists can still read those lists with recipient.displayName preserved and can still resolve the child through GET /users/{id} (a PersonSummary); everyone else gets 404 PERSON_NOT_FOUND. Archiving a list is DELETE /lists/{id} (owner or co-owner; the flag canDeleteList); an archived list is permanent (no unarchive). The child's active lists that the signed-in parent can see are the lists in GET /lists whose recipient is the child and whose status is ACTIVE or DRAFT.

Scope
1. Story D1: the Members section shows the owner and co-owner from the detail's own fields, then the roster.
2. Story D2: a pure child-deletion plan, a batch archive in ListService, and a session-safe deletion flow that archives the child's active lists one by one and then deletes the child.
3. Story D3: the Children screen UI for the flow, the corrected message, and the new-code UI rules.
4. Story D4: handoff and the real-mode check.

Decisions
- UI RULES FOR NEW CODE (banked polish backlog; they apply to everything new or rewritten in this package; older screens are not refactored): (1) every confirmationDialog is attached to the control or row that triggers it, never to a List, ScrollView, Form, NavigationStack, or screen container (the delete confirmation attaches to the child's row, so each row holds its own presentation state or is a small row wrapper view); (2) errors are scoped: a mutation error is thrown to the initiating view and held in its local state (shown as an InlineErrorBanner on the Children screen) and disappears on dismiss, retry success, or leaving the screen; nothing new is published in a shared service error that another screen reads; (3) destructive actions use role: .destructive with Color.destructiveColor (swipe action and context menu included, with an explicit tint); (4) errors use the existing InlineErrorBanner.
- Members section (D1): when the roster is shown (the flag canSeeMembers is true and members is present) the section lists first the OWNER row (from detail.owner) and the CO-OWNER row (from detail.coOwner, only if present), labeled "Owner" and "Co-owner", with NO Remove action, then the roster rows (members and viewers, labeled "Member" or "Viewer") with Remove only when the flag canManageMembers is true. The recipient is not listed as a row (the list header already says who the list is for). When the roster is NOT shown (viewers, public non-members), the section shows only the member count, exactly as today, and the owner and co-owner rows are NOT added (nothing new is revealed to anyone who was not shown the roster). The member count text keeps using memberCount (members and viewers only) and is worded "N members" for the roster rows only. Do not change who can add, remove, or leave; those flags decide. Update the existing roster-kind logic: roster rows are never the owner or co-owner under the new server rule, but keep the defensive handling so a roster entry that matches the owner or co-owner id is not shown twice (show it once, as the owner or co-owner row).
- Child deletion plan (D2): a pure nonisolated function plans the deletion from the child and the lists summaries: the plan is (a) deleteNow when the child has no ACTIVE or DRAFT list, (b) archiveThenDelete(listIds in a stable order) when it has some and every one of them has canDeleteList true, (c) blocked when any active list of the child has canDeleteList false (the message says an active list of this child can't be archived by the signed-in user and the person who owns it must archive it first). The lists come from the ListService's current lists after a fresh forced reload (refreshLists, or the equivalent forced fetch: never the cache alone), so the plan reflects the server. Archived lists never count.
- The flow (D2): an @MainActor coordinator (for example ChildDeletionFlow) in Features/Children, taking the ChildService and the ListService through the existing environment or an explicit init. Steps: reload the lists (forced), compute the plan, (the view has already shown the confirmation for that plan), archive each planned list in order through ONE batch method on ListService (archiveLists(ids:), sequential, stopping at the first failure, a single lists reload at the end even after a failure, nothing in the loop that publishes a shared error), then ChildService.deleteChild(id:). If any archive fails: STOP, do NOT delete the child, and report which lists were archived and which failed as counts only ("Archived 2 of 3 lists. The child was not removed."); the plan is recomputed from fresh data on Try Again, so already archived lists are skipped and the flow continues (idempotent). If the child delete then fails with 422 (a hidden active list), show the corrected message. A 404 on a list archive (already gone) counts as archived; a 404 on the child delete counts as deleted (the existing childNotFound handling). The flow checks Task.isCancelled between steps and never writes state after the session ended (the services' own generation guards apply: do not bypass them); a user switch or teardown during the flow stops it and shows nothing.
- Confirmation (D3): one confirmationDialog attached to the child's row. For deleteNow: title "Delete this child?", message "<display name> will be removed.", destructive button "Delete". For archiveThenDelete: title "Archive N list(s) and delete this child?" (singular when N is 1), message "<display name>'s active lists will move to Archived and can't be edited afterwards. Archived lists stay available there. This can't be undone.", destructive button "Archive and Delete". For blocked: no dialog; an InlineErrorBanner with the blocked message and no Try Again. The child's name appears only in the dialog message text, never in a log or identifier.
- Messages: ChildError.childHasLists becomes "This child still has active lists. Archive them first."; update its tests with this decision as the reason. While the flow runs: the child's row shows a progress state, the delete controls are disabled, and VoiceOver announces progress ("Archiving lists" then the result). After success the child leaves the list and the lists service shows the archived lists under Archived (it already reloaded). Partial-failure and other errors show as one InlineErrorBanner on the Children screen with Try Again where it makes sense and Dismiss.
- Accessibility and tokens: DesignSystem tokens only, 44-point targets, Dynamic Type, labels and hints; no names or ids in accessibility identifiers.

Non-goals: restoring or unarchiving a list (not possible), deleting archived lists, editing a child, changing who can archive, the polish and theme passes, items, purchases.

Acceptance
- The plan function has a full truth table (no lists; only archived lists; one active; several active; a DRAFT counts as active; one active list with canDeleteList false is blocked; lists of OTHER children and the signed-in user's own lists never count; stable order).
- Through the flow with fakes: deleteNow deletes the child; archiveThenDelete archives each list in order then deletes the child; a failure on the second list stops with the child not deleted and a counts-only message; Try Again after the failure recomputes the plan and finishes; a 404 on a list counts as archived; a 422 on the child delete shows the corrected message; cancellation or a user switch mid-flow writes nothing; nothing is ever deleted when an archive failed.
- The batch archive reloads the lists once, at the end, even after a failure, and does not publish a shared error.
- The delete confirmation is attached to the child's row, destructive and red, and the dialog text matches the Decisions for each plan.
- The Members section shows the owner and co-owner rows first when the roster is shown and never when it is not; Remove appears only on member and viewer rows with canManageMembers; a roster entry duplicating the owner or co-owner is shown once; the view-state truth table covers every flag combination and every roster shape (owner only, owner and co-owner, empty roster, a duplicate entry).
- No child or member name, id, or email is logged or sent to Sentry; the log-scan test still passes.
- No change under contract/, .claude/, any .pbxproj, the synced Docs files, or LocalPackages/TrackerAPI.

# Gate 1: Story D2, the deletion plan, the batch archive, and the flow
- Contract slice: DELETE /lists/{id} (archive), DELETE /users/me/children/{id} (L17), GET /lists (recipient, status, canDeleteList), client guide 6.6 and 7.10.
- Acceptance criteria: Decisions "Child deletion plan", "The flow", "Messages"; acceptance bullets on the plan, the flow and the batch archive.
- Scope (files): new Features/Children/ChildDeletionPlan.swift (pure), new Features/Children/Services/ChildDeletionFlow.swift, Features/Lists/Services/ListService.swift (add `archiveLists(ids:)` only), Features/Children/ChildError.swift (text), tests under ChristmasTrackerTests/Features/Children/ and Features/Lists/, Docs/reports/I3d-2-child-deletion-flow.md. The mock child repository may follow L17 (only ACTIVE or DRAFT lists block) if its tests are updated with that reason.
- New interface introduced: yes.
  - `nonisolated enum ChildDeletionPlan: Equatable, Sendable { case deleteNow; case archiveThenDelete(listIds: [String]); case blocked; static func plan(childId: String, lists: [GiftList]) -> ChildDeletionPlan }`; a list belongs to the child when `recipient.id == childId`; only ACTIVE and DRAFT count; stable order is the order of `lists`.
  - `ListService.archiveLists(ids: [String]) async -> ArchiveBatchResult` (nonisolated Sendable value: archivedCount, totalCount, failedIndex or failed id kept in memory only, error); sequential, stops at the first failure, a 404 counts as archived, one reload at the end even after a failure, publishes no shared error, session-safe.
  - `ListService.freshLists() async throws -> [GiftList]` (added because `refreshLists()` returns nothing and publishes failures in the shared `error`, so the flow could not tell a failed reload from an empty one): always fetches from the repository (never the cache), session-safe like the other operations (generation guard, `perform`, throws CancellationError when the session ended), writes the result to `lists` and the cache exactly as `refreshLists` does, publishes NO shared error, and returns the fetched lists (typed ListError on failure). The flow computes the plan from the RETURNED lists.
  - Scope addition found by the test-writer: `ChildService` exposes no session handle, so after a user switch (clearForSession) during the archive phase, `deleteChild` would capture the NEW generation and delete through the repository. `ChildService` therefore gets a read-only `private(set) var sessionGeneration: Int` (the existing `generation`, exposed for reading only, nothing else changes); the flow captures it (and the list service's equivalent if needed) at its start and stops with a nil result, never calling deleteChild, when it changed. ChildService.swift is added to the D2 file list for this one accessor.
  - Mock alignment (L17): `MockListRepository.removeChild` blocks on any list of the child; if the mock's `deleteList` archives (does not remove) a list, align it so only ACTIVE or DRAFT lists block and update its tests with this decision as the reason; if the mock's `deleteList` removes the list, leave the mock alone and record the gap as a deviation.
  - Error mapping in the flow result: list failures map to the same-named ChildError cases (forbidden, unauthorized, rateLimited, network, invalidResponse, server, sessionEnded; anything else to `server`); a ListError.notFound on an archive counts as archived.
  - `@MainActor final class ChildDeletionFlow` with `run(childId:) async -> ChildDeletionResult` and the typed result `deleted`, `archivedThenDeleted(count)`, `partialFailure(archivedCount, totalCount, error)`, `blocked`, `failed(error)`, plus a `plan(childId:) async` step so the view can show the right confirmation; nothing is published in a shared property.
- Full pipeline.
