## Contract issues found
- None filed in Docs/contract-issues.md (the file is unchanged). No server-versus-contract disagreement could be observed: the real-mode check has not been run. Three places where the synced documents disagree with each other or are silent (for the API team, detail in Docs/reports/I4b-1-regenerate.md and Docs/epics/I4b-manage-purchase.md, "Inventory"):
  1. **Clearing a tracking number is not specified.** Docs/client-guide.md 7.7 only shows setting it; the spec types `trackingNumber` as a plain string (max 100) with no null or clear semantics for `updatePurchase` and `updatePurchaseShipping`. The client treats an empty tracking field as "unchanged" and never sends an empty string for it, so a user cannot remove a tracking number once saved. QUESTION: how should a client clear it (empty string, null, or not at all)? Notes clearing is specified (an empty string; null is a 400).
  2. **Guide wording on the delete response.** Docs/client-guide.md:673 says the delete response "does not include the item", while the spec (`deletePurchase` 200 refs `Purchase`, which has the required `item {id, name, listId}`) and S14 say it does. The client decodes the spec shape.
  3. **getPurchase description.** contract/openapi.json:4424 says "purchaser or list owner only"; S14 and P11 say anyone but the purchaser gets 404 PURCHASE_NOT_FOUND. The client opens only the purchaser's own purchases and treats every 404 as gone.
- Also for the API team (not a contract row): an UNREADABLE body on a documented error status is mapped by status; 401 and 429 never reach the repository as responses because the refresh and rate-limit middlewares turn them into thrown errors (reviewed, no change).
