## What changed
- **K0 (2d4baec):** in real mode the app no longer falls back to mock data. If the generated client cannot be built, a blocking screen shows ("This version can't connect to the server. Please reinstall the latest version."), nothing else, no sign-in, one category-only Sentry event, and every repository is an inert one that throws. `AppDependencies.make()` was deleted. `ListService` keeps a session-local deleted-ids guard (an in-flight load can no longer bring a deleted list back), has separate `isLoadingLists`, `isLoadingDetail` and `isMutating` flags, and drops a list that the server reports gone; the detail and edit screens leave when their list is gone (`goneListId`). Log hygiene: no Log call in `Features/` interpolates a list id, list name, email, or person value, enforced by a text-scanning test with an empty allowlist.
- **M1 (6614f25):** pure domain models (members, children, co-owner change), member and child errors with plain messages, and the flag-driven view-state functions (Members section, per-row Remove, Leave, co-owner section, children, recipient options, form validation) with a truth table; the only roster-row role read is inside the members view-state file.
- **M2 (47bd3e6):** `GeneratedClientMemberRepository` and `GeneratedClientChildRepository` (every documented response mapped, tested through the real factory-built client), the co-owner change through update-list (set only), `ListService` add, remove, leave and set-co-owner (refetch after add and remove; leave drops the list everywhere), `ChildService`, mocks with privacy scenarios, a 7th session clearable (the pinned count moved 6 to 7 because `ChildService` holds the signed-in user's children).
- **M3 (3e1954a):** the Members section, Add member sheet, Leave list, the co-owner control in Edit list, the Children screen under Profile ("Family" section), and the recipient picker in Create list.
- **Guard fix (I3b-6):** the deleted-lists guard is now a sequence, not a session-long id set. `ListService` keeps a session-local counter; every list load, refresh, detail load, update and member refetch captures it at its start; a completed delete, leave, or gone-list drop (notFound, archivedReadOnly) bumps it and records the value for that list id. A result is filtered only when its list was removed AFTER the operation started. So a load that starts after a leave completes shows the list again when the server returns it (leave, re-add, later load works), while a load already in flight when the removal completed still cannot resurrect it. A deleted list is still hidden on every later list load because the server returns it as ARCHIVED and the archived filter hides it. The counter and the records are cleared at teardown with the session generation. Replaced tests are listed in Docs/reports/I3b-6-guard-fix.md.
- **Cached-detail revalidation (I3b-6):** `loadListDetail` still shows a cached detail first and always revalidates. If the revalidation fails with notFound, archivedReadOnly, or forbidden (forbidden only when a cached detail was shown), or the guard drops the result, the cached detail, the list entry and the open detail are removed, `goneListId` is set (the detail and edit screens leave on it) and the error is reported. A forbidden with no cached detail changes nothing, as before. A cached detail does not survive teardown or a user switch.
- **I3b-2 (bc5657a, 7f0039b, aedc89d, ef27275):** the client is regenerated from contract revision 28 (the derived-spec guard held at 5 transformed properties; the diff adds only the `removeCoOwner` path). `ListRepository.removeCoOwner(listId:)` and `ListService.removeCoOwner(listId:)` call the generated DELETE operation (every documented response mapped, tested through the real factory-built client); the service updates the open detail, the list entry and the cache from the RETURNED detail without a refetch and is session-safe like the other list mutations. `CoOwnerChange.clear`, the repository's typed refusal and `CoOwnerSectionState.clearingSupported` are gone. The edit screen's co-owner section now shows "Remove co-owner" (confirmation dialog) when `canSetCoOwner` is true and a co-owner exists; on success the sheet stays open and the section updates; notFound and archivedReadOnly leave the screen; "Try Again" re-runs whichever action failed (an acceptance review caught that it re-ran Save after a failed removal; fixed). ## Open risks and deferred items
- **Unverified on screen:** no agent ran any new screen in the simulator or against the backend (no agent could log in). The screens, including the new "Remove co-owner" action, are verified by view-state tests, text-scanning tests and reviewers reading the code. Brian's real-mode check below is the first run.
- **Remove co-owner (I3b-2), reading only:** the confirmation dialog and its text, the sheet staying open after a removal, the section updating from the service's detail, and the "Try Again" re-run of a failed removal are covered by pure view-state tests and source scans, not by a running app or a UI test. After a removal the sheet's snapshot still drives the Save diff (name, theme, visibility); that cannot send a co-owner change, but a redundant name or theme value is possible if another client changed them meanwhile.
- **K0 behavior changes to know:** `loadListDetail` now shows the cached detail first and ALWAYS revalidates with the server (one extra GET per open); a spurious 404 hides the list only from loads that were already in flight (a later load shows it again if the server returns it); `goneListId` notifies only on a value change, so a second "gone" report for the same id in one session does not re-fire the automatic screen exit (the error banner with its Leave action still shows).
- **Double submission:** the service does not guard against double submission of add, remove or leave; the views disable the controls while `isMutating`, and the sheets gate Save with `canSubmit`. `isMutating` is a Bool, so overlapping operations could flip it early (existing pattern).
- **`goneListId` is still cleared only at the session reset** (found by the guard fix review, not changed): if a user leaves list X (`goneListId` = X), is re-added, opens X and X is then reported gone again, `goneListId` is still X, so the screens' `onChange` does not fire and the automatic exit does not happen (the error banner with its Leave action still shows). Same limitation as the existing note above.
- **A later detail load of a deleted list is not filtered by status:** the list-of-lists path hides ARCHIVED lists, but `loadListDetail` shows whatever detail the server returns. After a delete, a later detail load shows the list if the server returns an archived detail instead of notFound or archivedReadOnly. Please confirm on the real backend what it returns (step 5 deletes a list).
- **Reviewed by reading only (not exercised):** Dynamic Type behavior, the VoiceOver delete action, the simultaneous edit-sheet dismissal plus detail pop when a list is gone, and a 404 with an empty or non-JSON body from the member calls (the code falls back to a plain not-found).
